# 安全策略 · Security Policy

## 报告漏洞 · Reporting a vulnerability

请通过本仓库的 **GitHub Security Advisories**(仓库 **Security → Report a vulnerability**)私密报告安全问题。**请勿**在公开 issue、PR 或讨论区披露未修复的漏洞。

Please report security issues privately via this repository's **GitHub Security Advisories** ("Security → Report a vulnerability"). Do **not** disclose unfixed vulnerabilities in public issues, PRs, or discussions.

## 威胁模型速览 · Threat model at a glance

如意 Ruyi 是**本机单用户**工具,安全设计围绕「本地服务不外泄 + 危险操作可控可撤销」。下面每一条都写明**它防什么、不防什么**:

- **仅回环监听 + 页面 token(防浏览器里的网页,不防本机其他进程)**:HTTP 服务默认只绑 `127.0.0.1`;`--host` 绑任何非回环地址必须**显式再加 `--allow-remote`**,否则启动即拒绝。变更类请求需要页面拿到的 token,并有 Host 白名单、同源校验、`X-Frame-Options` / `frame-ancestors`(禁被嵌入)、`X-Content-Type-Options: nosniff`、脚本不带 `unsafe-inline` 的 CSP,挡的是**跨站网页 / DNS rebinding / 点击劫持 / 被嵌入**这一类。即使放行了远端监听,非本机对端也拿不到页面 token(`/api/bootstrap` 与页面注入都拒),其余接口必须自带头 token。**它不防同一台机器上的其他进程**:`127.0.0.1` 没有按用户区分的访问控制,本机任何进程都可以无凭据 `POST /api/bootstrap` 取得 token(页面靠这条握手拿 token),loopback 非浏览器调用对会话类接口(同源即可)也不要求 token;带 `127.0.0.1` 主机权限的浏览器扩展同理(扩展读响应不受 CORS 约束)。因此**不要在多用户共用的机器(远程桌面 / 终端服务器)上运行**,也不要装来路不明的浏览器扩展。
- **权限分级 + 可撤销操作**:权限模式分档;写文件、执行命令等操作在动手前记入**检查点 journal**,可逐条回滚。计划模式下变更需显式批准。
- **自动档的拦截是规则判据,不是沙箱**:「智能自动」档对删除、安装、推送、对外发送、付款一类动作的拦截,依靠对命令文本的**规则匹配**(加管家按规则代批),能覆盖常见写法;但规则永远可以被绕过(拆开拼接的字符串、同义写法、经脚本或别的程序间接发起……)。想让每一步都经你确认,请切到「每步都问」;「全自动」不拦任何东西。把它当作降低误操作概率的护栏,而不是防恶意提示注入的隔离。
- **联网工具 SSRF 防御**:`web_fetch` / `http_download` 等拒绝私网、回环、链路本地等地址段,防止模型被诱导探测内网。它**只拦内网方向**:公网目的地不拦,被提示注入的模型读到本地内容后,仍可能经 URL 把内容带出去。
- **解压护栏**:zip 解压有条目数、解压总量、单条目 inflate 比上限,防 zip 炸弹。
- **工作区路径护栏(取决于权限档)**:在「每步都问」「改文件不问」档,文件工具受工作区根约束,阻断路径穿越到工作区之外(符号链接 / junction 按真实路径判)。在「智能自动」「全自动」档文件工具是**宽写模式**:不再限定工作区,只有一份「系统关键目录 + 会被自动执行的落点」名单(git hooks、`.vscode`、`.github/workflows`、CLI 配置等)被拒 —— 名单会随版本补充,但它不是工作区约束,也不可能穷举。设置里打开 `allowOutsideWorkspace` 同样不受限。执行类工具(脚本 / PowerShell / shell)本身就是任意代码执行,从不受工作区约束。**只在你信任的文件夹里打开工作区**:工作区里的项目配置(角色、技能、MCP 声明、Git hooks 等)会被如意读取并影响行为。
- **密钥掩码与落盘**:provider API key 在 `/api/status` 等响应中以 `••••<后4位>` 掩码返回,响应不含明文。磁盘上的 `config.json`、`config.json.prev`(恢复用的上一份,同样含真 key)与 `runtime.json`(本次运行的接口 token)是**明文**:POSIX 上权限为 `0600`(仅属主),Windows 上依赖用户目录自身的 ACL,请不要把数据目录放在共享位置或随意打包分享。
- **导入的会话文件视为不可信**:导入 JSON 时,文件里的 `cwd` 一律丢弃(会话落在当前默认工作区),导入的消息打 `meta.imported` 来源标记并丢弃文件自带的 `meta`;服务端对带 `messages` 的创建请求还会校验 `cwd` 必须在已配置工作区内。导入的对话内容仍会作为上下文进入模型,请只导入你信得过的来源。

Ruyi is a **single-user, local** tool. Its design centers on "the local service never leaks + dangerous actions stay controllable and reversible". Each control below says what it does and what it does not:

- **Loopback only + page token (protects against web pages in your browser, not against other local processes).** The HTTP service binds `127.0.0.1` by default; `--host` with any non-loopback address is refused at startup unless you also pass `--allow-remote` explicitly. State-changing requests need the page token, backed by a Host allowlist, same-origin checks, `X-Frame-Options` / `frame-ancestors`, `X-Content-Type-Options: nosniff` and a CSP without `unsafe-inline` scripts — aimed at cross-site pages, DNS rebinding, clickjacking and embedding. Even when remote binding is allowed, non-local peers never receive the page token (`/api/bootstrap` and the page injection both refuse) and must bring the header token for every other endpoint. **It does not protect against other processes on the same machine**: `127.0.0.1` has no per-user access control, any local process can `POST /api/bootstrap` without credentials to obtain the token (that handshake is how the page gets it), loopback non-browser calls need no token on the session-level endpoints (same-origin is enough), and a browser extension with host access to `127.0.0.1` is in the same position (extensions read responses regardless of CORS). Do **not** run it on a shared multi-user machine (RDS / terminal server) and do not install untrusted browser extensions.
- **Tiered permissions with a rollback-able checkpoint journal**: file writes, command execution and similar actions are recorded before they run and can be rolled back one by one; plan mode requires explicit approval for changes.
- **The auto tier's gate is a rule heuristic, not a sandbox.** In the default "Smart auto" tier, blocking of deleting, installing, pushing, sending outbound or paying relies on **pattern rules over the command text** (plus the steward approving under its own rules). It covers common phrasings, but rules can always be evaded (split-up strings, synonyms, indirection through scripts or other programs). To confirm every step, switch to "Ask me every step"; "Fully automatic" gates nothing. Treat it as a guard rail against honest mistakes, not as isolation against a malicious prompt injection.
- **SSRF defenses on networked tools**: `web_fetch` / `http_download` reject private, loopback and link-local ranges. They only block the *inward* direction — public destinations are not blocked, so a prompt-injected model that has read local content can still carry it out via a URL.
- **Zip-extraction limits** (entry count / total size / per-entry inflation ratio).
- **Workspace path guards depend on the permission tier.** In "Ask me every step" and "Edit files without asking", file tools are confined to the workspace roots (symlinks / junctions are judged by real path). In "Smart auto" and "Fully automatic" they run in **wide-write mode**: not confined to the workspace; only a list of critical system directories and auto-executed drop points (git hooks, `.vscode`, `.github/workflows`, CLI config, …) is refused — the list grows over time but it is not a workspace confinement and can never be exhaustive. `allowOutsideWorkspace` lifts the guard as well. Execution tools (script / PowerShell / shell) are arbitrary code execution and are never workspace-confined. **Open only folders you trust**: project config inside a workspace (roles, skills, MCP declarations, Git hooks, …) is read by Ruyi and influences behavior.
- **Key masking and storage**: provider API keys are masked as `••••<last 4>` in API responses. On disk, `config.json`, `config.json.prev` (the recovery copy, real keys too) and `runtime.json` (this run's API token) are **plaintext**: mode `0600` on POSIX, user-profile ACLs on Windows — keep the data directory out of shared locations and do not bundle it for sharing.
- **Imported session files are untrusted**: on import, the file's `cwd` is dropped (the session lands in the current default workspace), imported messages are tagged `meta.imported` and any `meta` shipped in the file is discarded; the server also checks that `cwd` on a create-with-`messages` request lies inside a configured workspace. Imported conversation text still becomes model context — import only from sources you trust.

## 边界与非目标 · Boundaries and non-goals

如实告知:

- **不是多租户服务。** 本机单用户工具,不提供跨用户隔离、账户体系或网络级鉴权。请勿把它当作对外网络服务部署;`--allow-remote` 只是「允许监听」,不是鉴权方案。
- **模型输出仍可能有害。** 权限模式与人工审查是**用户的责任**;放宽权限档意味着你承担相应风险。
- **桌面控制 MCP 权力很大。** `ai-computer-control` 能操控鼠标键盘、窗口、文件与外部程序。新装默认的「智能自动」档会尝试在删除数据、装卸软件、推送、对外发送、付款这类危险操作前停下来(其中非底线项可能由管家按规则代批,付款 / 关机 / 外发等底线项等你本人确认),但这是上面说的**规则判据**,不是保证。要每一步都由你确认,切到「每步都问」;放宽到「全自动」请谨慎,并优先在计划模式下审查。
- **更新包没有签名。** overlay 更新包(增量更新 zip)里自带清单与 `Manage-Overlay.ps1`,没有独立的信任根或签名校验,套用时脚本会被直接执行。**只套用你从可信渠道拿到、并核对过来源与哈希的更新包**;能调用更新接口的调用方(持有 token 的本机进程)可以让它套用任意路径的包。
- **Kimi 引擎下,接口 token 在 CLI 进程环境里。** Claude 引擎路径把回环凭据(`WCW_TOKEN` 等)只写进该会话 `--mcp-config` 里桥接 MCP 子进程的 env 块,并从 CLI 自身进程环境中删除,模型经 CLI 的 shell 起的子进程读不到。Kimi Code 没有按回合的 MCP 配置参数(只读全局 `~/.kimi-code/mcp.json`),回合级回环字段只能靠 Kimi 进程环境继承,所以 **Kimi 引擎下模型起的 shell 子进程可以读到 `WCW_TOKEN`**(一句 `env` 即可)。这与上面「不防本机进程」是同一类边界,需要时请改用 Claude 引擎。
- **命令行上的动态文本不是用来承载不可信内容的。** 经 `.cmd` 垫片起 CLI 时,`--agents` / `--append-system-prompt` / 工具清单里的 `%`、`!` 会被换成全角以防 cmd.exe 展开;路径类实参无法这样处理,请不要在含 `%` / `!` 的文件夹名下打开不可信的项目。

Stated plainly: this is **not** a multi-tenant service — a single-user local tool with no cross-user isolation, accounts, or network auth; do not deploy it as a public network service (`--allow-remote` only permits listening, it is not an authentication scheme). Model output can still be harmful — permission modes and human review are the **user's** responsibility. The desktop-control MCP is powerful (mouse/keyboard/windows/files/external apps); the default Smart auto tier *tries* to stop before dangerous operations such as deleting data, installing software, pushing, sending outbound or paying (the steward may approve non-floor items under its rules; floor items like payment, shutdown and outbound sending wait for you) — but that is the rule heuristic described above, not a guarantee. Switch to Ask me every step to confirm every step; loosen to Fully automatic deliberately and review under Plan only.

- **Update packages are unsigned.** An overlay update zip ships its own manifest and `Manage-Overlay.ps1` with no independent root of trust or signature check, and the script is executed when applied. Apply only packages obtained through a trusted channel whose origin and hash you have verified; any caller holding the token (a local process) can make the update endpoint apply a package from an arbitrary path.
- **With the Kimi engine the API token lives in the CLI process environment.** On the Claude path the loopback credentials (`WCW_TOKEN` etc.) are written only into the env block of the bridge MCP child inside the per-session `--mcp-config` and removed from the CLI's own process environment, so subprocesses the model starts through the CLI's shell cannot read them. Kimi Code has no per-turn MCP config flag (it reads only the global `~/.kimi-code/mcp.json`), so turn-scoped loopback fields can only be inherited through the Kimi process environment — **under the Kimi engine, shell subprocesses started by the model can read `WCW_TOKEN`** (a plain `env` shows it). This is the same class of boundary as "does not protect against local processes" above; use the Claude engine if that matters.
- **Dynamic text on the command line is not a place for untrusted content.** When the CLI is launched through a `.cmd` shim, `%` and `!` in `--agents` / `--append-system-prompt` / tool lists are replaced with their full-width forms so cmd.exe cannot expand them; path-like arguments cannot be treated that way — do not open untrusted projects under folder names containing `%` or `!`.
