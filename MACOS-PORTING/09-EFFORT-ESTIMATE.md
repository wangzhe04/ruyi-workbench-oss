# 工作量评估与排期

## 1. 估算结论

完整 Apple Silicon 原生首发，从平台基线到可分发的离线桌面版：**基础 60–96 人日，含一次性风险预留约 72–125 人日**。更合适的首个投入边界是 M1 浏览器内测版：**基础 26–40 人日，含预留约 32–52 人日**。

以上保留立项时的全项目预算。2026-10-30 已完成 P0 基线与探针，剩余区间见下方检查点；仍不是合同工期或统计上的 P50/P90。下界要求接口选择顺利、核心共用业务没有重大潜在缺陷；上界允许合理范围内的平台返工。重大范围变化仍需重估，不保证落在该区间。

## 2. 口径与假设

- 1 人日 = 8 小时项目工作；包含设计、实现、相关测试、常规缺陷修复、独立复核响应和文档，不只计算写代码时间。工时包括开发及验证贡献者的合计，不是每个人各花同样的天数。
- 开发者熟悉 Node/子进程/MCP，团队至少有人能处理 Python 与 macOS 原生 API。已有 AI 编码工具可辅助，不预设固定提效倍数，真机授权、调试、版式检查和发行验证仍占时间。
- Apple Silicon arm64 首发；拟以 macOS 14 为最低版本，P0 保留为目标，尚未完成最低系统运行验证。保留 Windows 原能力与 CI；没有要求同时重写业务架构。
- 可获得标准用户 Mac 测试环境、最低/较新系统版本、Windows 回归环境、双屏/Retina 测试条件；P0 开始准备 Developer ID 签名账户及公证权限。
- 用户自备 Claude/Kimi 和模型端点，不把官方 CLI 放进离线包。真实外部机器人服务账户与联调窗口由环境提供方准备；缺少时只算假端点联调，不声称实弹验收通过。
- 首发更新以整包替换、数据备份和回退为准；不包含另建在线自动更新服务或通用跨平台增量 overlay 系统。
- 包内 Office 能力指文件生成/读取/图表及明确场景，不包含任意宏、插件、公式引擎或 Windows 专用 Office 自动化行为兼容。

## 3. 分阶段估算

| 阶段 | 基础人日 | 工作量形成原因 | 当前判断把握 |
|---|---:|---|---|
| P0 基线与方案冻结 | 4–6（原预算） | 已交付基线、接口、宿主/权限/依赖探针；实际人日未核算 | 已完成设计/基线 |
| P1 运行时与系统边界 | 8–12 | 路径与权限、shell、进程树、启动/探测，影响面广 | 中 |
| P2 Agent、凭据与核心业务 | 8–12 | CLI/MCP 适配、Keychain 和恢复、管家/调度/机器人联调 | 中偏低 |
| P3 文档、浏览器与模板 | 6–10 | 库主体可复用，主要在依赖拆分、字体和真实产物验证 | 中 |
| P4 Mac 桌面壳 | 10–16 | 原宿主不可复用，窗口/系统桥/媒体/生命周期需新实现 | 中偏低 |
| P5 Mac 桌面自动化 | 16–26 | AX/截图/输入/OCR/宏与多屏、焦点、权限的组合验证 | 低 |
| P6 离线打包与发行 | 8–14 | 原生依赖闭包、签名公证、干净机、迁移回退与总回归 | 中偏低 |
| **总计** | **60–96** | 各工作包只计入一个阶段 | — |

工作包的人日加总见 [TASKS.json](TASKS.json) 与各阶段表。P0 的探针只负责识别可行方案，不抵消后续正式实现；P1–P5 计各自专项测试和复核，P6 计最终组合/安装/迁移回归，不重复计算同一专项测试开发。

预算公式：低端 `ceil(60 × 1.20) = 72`，高端 `ceil(96 × 1.30) = 125`。20%–30% 是给跨系统联调和未知平台行为的一次性储备，不再逐阶段重复相乘。人日区间不是由文件数、代码行数或“复用百分比”推出来的。

## 4. 可选投入边界

以下保留立项时从 P0 开始的原始**累计**预算，不能再把各行相加，也不是 P0 完成后的剩余预测。

| 交付边界 | 阶段范围 | 基础人日 | 含 20%–30% 预留 | 单人全职日历 | 两位互补开发者日历 |
|---|---|---:|---:|---:|---:|
| M1 浏览器内测 | P0–P3 | 26–40 | 32–52 | 7–11 周 | 5–8 周 |
| M2 独立桌面内测 | P0–P4 | 36–56 | 44–73 | 9–15 周 | 6–10 周 |
| M3 桌面自动化候选 | P0–P5 | 52–82 | 63–107 | 13–22 周 | 9–14 周 |
| M4 离线正式发行 | P0–P6 | 60–96 | 72–125 | 15–25 周 | 10–16 周 |

单人按每周 5 个项目工作日粗算并向上取整。双人方案按约 1.6 人的有效并发能力粗算，再给串行验收留出余量，**不直接除以 2**：平台契约、共享大模块、权限真机验证和阶段集成无法完全并行。独立复核与测试时间已计入人日，需排出相应人力，不应被当作免费额外产能。

日历估算不包括节假日、兼职占用、硬件采购、账户开通、公证服务不可用、等待真实服务联调窗口等外部等待。未确定开工日期和资源到位日期，因此不虚构具体发布日期。

M1/M2 是需要按说明准备运行环境的内测版。若要跳过桌面自动化、提前发布可安装的“基础正式版”，需要单独裁剪 P6 并验证其离线依赖/签名/升级范围；不能把 M1 的估算直接称为正式发行工期。

## 5. 分工和关键依赖

两人配置建议：A 负责平台运行时、Agent/凭据、数据与发布整合；B 负责 Python/文档/浏览器、Mac 宿主和桌面自动化。两者交叉复核，并安排实际测试时间。即使使用 AI 子代理，也不要同时无协调地改写 `01-config`、`04-permission-runtime`、`12-tool-dispatch`、`13-http-router` 等共享文件。

关键依赖链：**P0 契约 → P1 安全执行 → P2/P3 可交付业务 → P4 稳定宿主/权限身份 → P5 桌面操作 → P6 干净机发行验收**。

可提前的工作：

1. P0 即确认签名账户、SDK、测试设备与真实 CLI 环境，做 Keychain/TCC 原型。
2. P1 期间，另一人可在 P0 契约下做 P3 Windows 依赖拆分和文档样例；其运行验收等 P1。
3. P2/P3 期间，可做 P4 宿主 UI 原型和 P5 AX/OCR 探针；服务管理/安全桥仍等接口稳定。
4. P3 冻结依赖版本后立刻试打离线包，提前发现 wheel 架构、签名和浏览器资源问题；正式 P6 不再承担首次探索。

## 6. 主要风险与重估触发

| 风险 | 早期验证 | 超出基础估算的触发条件 |
|---|---|---|
| Mac 子孙进程停止不可靠 | P0/P1 真实父子孙与 CLI/MCP 探针 | 必须支持未知程序脱离进程组且仍承诺完整回收；需要新的原生治理方案 |
| Keychain/TCC 身份不稳定 | P0 helper，P2 保护器，P4 签名身份 | App/helper/Python 权限归属反复变化，升级后密钥访问不兼容 |
| WKWebView 媒体或浏览器行为不满足 | P0 最小真实界面原型 | 需要更换宿主；重新做安全桥、打包和媒体验收 |
| AX 在目标应用不可用 | P0/P5 目标应用探针 | 从标准应用扩大为任意企业应用、后台/锁屏操作或严格 UIA 等价 |
| 离线依赖无法闭合 | P0 wheel 探针，P3 版本冻结 | 无可用架构 wheel、需要源码构建/替换库，或最低系统版本降低 |
| 核心历史问题超出平台改造 | P0 同 SHA 双平台基线 | 全量回归发现大量双方均存在的业务缺陷，需另开维护任务 |

上述风险先消耗统一储备；只有范围变化或预计储备不足时重估，不把“风险追加天数”和储备机械叠加。P0、M1、M2 三个节点重估剩余工作，记录新增证据、已花人日和剩余区间，而非用原总额减掉已花时间当作新预测。

## 7. 可选增量与未计费用

| 可选范围 | 粗估增量 | 条件 |
|---|---:|---|
| Intel x64 原生包与回归 | 8–14 人日 | 共用架构不变，有真实 Intel 机器、可用运行时和 wheels；否则重估 |
| 降低最低系统版本，额外支持 macOS 12/13 | 5–10 人日 | 需验证 API 与依赖可用性；仅是初步量级，不构成兼容承诺 |
| 新建 Mac 自动增量更新/签名更新渠道 | 8–15 人日 | 不含服务器持续运营；原 Windows overlay 不能直接当 Mac 更新器 |

新增范围有交叉时不能简单相加，应重新拆包。Mac App Store、任意 Windows 应用兼容、广泛企业软件自动化缺少足够需求依据，不给虚假精确数字。

预算不含 Mac 硬件、Apple 开发者账户、商业应用许可、模型调用、CI 资源和长期维护。若使用综合人日单价 `D` 元，完整首发人工预算可先按 **72D–125D 元**规划；缺少团队单价时不臆造金额。

## 8. P0 后估算检查点（2026-10-30）

| M1 浏览器内测 | P1–P3 | 22–34 | 27–45 |
