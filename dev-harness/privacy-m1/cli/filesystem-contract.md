# Strict filesystem feasibility contract

This experiment is separate from the product and from the existing bounded AAP test. A passing infrastructure run means that observations and cleanup were collected; it does not mean strict isolation passed.

The proposed protected view consists of an owned, immutable model projection, an owned writable output/home/cache tree, and an explicit list of indispensable read-only Windows/runtime resources. Runtime exceptions are part of the contract and must be inventoried separately. A host user's original files are outside this view regardless of their DACL, including grants to Everyone, ALL APPLICATION PACKAGES (AAP), ALL RESTRICTED APPLICATION PACKAGES (ARAP), or an application SID. No real user file or registry secret is probed.

Each permitted/forbidden operation must execute in both the root and a real child process, after positive controls establish that the synthetic fixture exists and is readable on the host. Root and descendant package/capability identities are checked independently. Denial requires an actual failed syscall from a running probe; absence of probe output, process startup failure, timeout, or a missing target is unknown. Reads, directory enumeration, writes and name aliases are distinct observations. A finite negative matrix cannot establish an exclusive filesystem allowlist.

Synthetic fixtures cover ordinary-user-only, Everyone, AAP, ARAP and profile SID grants outside the projection. Junction/reparse and hardlink cases target only owned temporary fixtures. A junction created by the contained process after launch avoids accidentally propagating a projection grant into its target during host setup. Hardlink construction is a deliberately unsafe projection-maker negative control: names share a file's identity and security descriptor, so granting a linked projection file can also grant its outside name. It must be reported separately from token behavior. A production projection maker must reject links/reparse points and bind file identity; lexical prefix checks do not establish that property.

AppContainer profile storage is another explicitly tested resource, not implicitly part of the output directory. Only a newly created, unique test profile may contain a synthetic storage marker. The helper owns profile cleanup. A fresh profile does not establish a constrained registry view or exclude all other host resource classes.

## Candidate mechanisms and limits

* LPAC opts out of ordinary AAP resource authorization. It remains a DACL-based dual-principal boundary, not a path namespace. ARAP and profile grants require explicit negative controls.
* `CreateRestrictedToken` can add a restricting-SID access check or disable existing SIDs. `WRITE_RESTRICTED` only constrains writes and cannot satisfy the read contract. For an already restricted token, the documented restricting list is the intersection, so adding a fresh SID cannot be assumed to add an independent third check. A random restricting SID also removes access to required Windows resources whose DACL lacks it. Granting that SID across system/user directories is outside this experiment's authority. The bounded candidate derives a primary token from the caller's own token, disables maximum privileges, uses one random restricting SID, and grants that SID only on its projection/output. It calls `CreateProcessAsUserW` with the existing LPAC attributes and verifies the suspended root still carries exactly that restricting SID before resuming. No thread impersonation or privilege enabling is used. Missing privileges, incompatible token attributes or failure before JS are blockers, not successful isolation.
* A token has no supported arbitrary path-deny field. Its default DACL controls newly created objects. The token object's own DACL controls access to token handles. Neither restricts access to pre-existing files. Deny-only SID attributes consume matching deny ACEs in object DACLs; they do not create path rules.
* A process-side file wrapper, preload, environment variable, or broker convention is not an OS boundary against the same process's direct syscalls or descendants. It can supply a mediated API only after all direct access is constrained.
* A separate OS file namespace (for example a VM with only explicit projected shares), or an installed privileged filesystem enforcement component, remains a candidate if the unprivileged native mechanisms cannot meet the contract. This report does not claim such an environment is installed, verified, or sufficient without its own inheritance, mount/share, network and cleanup tests. Ordinary WSL filesystem access, including host drive mounts, is not automatically a strict boundary.

No system/user directory ACL, firewall, loopback exemption or installed program is modified. There is no elevation, dependency installation or download. All process homes and both AppData locations point to the owned output tree. The runner uses the repository's `killOwnTree` and validated `safeRemove` lifecycle utilities.
