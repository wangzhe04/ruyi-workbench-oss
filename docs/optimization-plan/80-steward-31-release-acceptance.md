# 3.1 发布前验收：升级、全新数据目录与实际离线包

更新：2026-10-18。接续 [79 号源码收口](79-steward-31-source-closure.md)。本次验证未发布候选代码，沿用当前源码的 `3.0.1` 内部版本元数据；本地先后构建 `31qa`、`31qb`，补齐收尾与回执边界后再构建 `Ruyi-31qc-slim.zip` / `Ruyi-31qc-full.zip`。各版分别保留，以源码与产物 SHA-256 标识候选身份。

## 发现与修复

- 首轮 Windows 全回归为 526 通过、1 失败、1 flaky、527 实跑、7 opt-in live 跳过；单测 2030 通过、26 跳过、0 失败。唯一失败是截图件迁到共享浏览器夹具后，旧清册仍要求两件直接启动浏览器。现精确锁定唯一的 `dom-smoke`，保留独占桶和清理检查。
- `surface-hardening-w2` 首跑的 P6 抖动来自健康响应早于异步 `runtime.json` 落盘，以及相邻端口探测没有绑定进程。现等待 B 自己持久化的 PID、实际端口与 overlay 身份，原 A 存活及未接管断言保持。
- `release-dryrun` 原来忽略构包非零，可能按残留 stage 报通过。现构包失败、ZIP 缺失、不可读或缺文件都失败；Full 显式要求时不可跳过。源码运行包与真正的 EXE 包分别验收。
- 桌面壳原先共享全局 Mutex 和真实用户的 WebView2 目录，隔离副本无法与已有窗口并存。现在只有显式 `RUYI_HOME` / 旧兼容变量使用独立 Mutex 与 `<dataRoot>/desktop/EBWebView`；默认启动保持原路径。相对路径按安装目录解析，单前导斜线使用安装目录所在盘，拒绝含糊的 `C:folder`，后台继承同一个绝对根。
- 新桌面状态子树纳入原生文件工具的敏感读、写和搜索排除。真实 HTTP 验证嵌套状态无法读写或搜索，普通工作区中的 `desktop` 文件夹仍可读写搜索。原先使用显式数据根的用户会建立新的浏览器状态，浏览器侧界面偏好需重新选择；服务器配置与会话仍沿用原数据目录。
- 第二轮完整回归为 527 通过、0 最终失败、3 flaky，残留测试浏览器 0。停止测试重启时取到旧 token，现必须同时匹配当前 ChildProcess 的 PID、端口及健康 overlay 后才采纳 runtime token，不删旧 runtime 遮掩时序。
- 长文本 flaky 暴露实际收尾竞态：provider 已离开 `activeChildren`，最终助手消息仍在异步保存，信封却报 `live=false`，只靠轮询的界面会停在旧历史。现在既有 `turnSettlers` 所有权释放前仍报 live。确定性单测暂停真实回合的 `DeliveryHooks.capture`，确认 child 已退出、owner 仍在且盘上尚无助手消息；修前稳定失败，修后释放后读到真实末消息、live/execution 结束且 ETag 变化，未延长浏览器测试等待掩盖问题。
- 机器人设置测试的首句等待还揭示迟到到访可能清掉新回复的窗口。到访现在核对期间新增用户行的 revision，并保留到访开始时已在发送的界面；同样覆盖排队、手选递话和恢复回执。新浏览器回归扣住真实到访响应，先显示真实配置卡，再释放并等待旧分支的历史请求完成，要求原用户行和原卡仍连接 DOM。仅关闭保护的反向验证恰好 S1b 一项失败，恢复后整件通过，没有重发首句。
- 独立复核进一步补齐到访期间新收到的直递回执和原行就地结算：revision 跟踪实际新增对话行及当前 feed 内的回执结算，纯语言重画不计新活动。另两条浏览器 gate 确认原行仍在、状态已结算且目标线程只执行一次；退回仅用户行计数时两条新断言及关联行数断言失败，恢复后整件通过。
- `31qb` 的 Full 实际包核心旅程中，`session-get-etag` 的 H3/F1/F2 失败；报告和日志保留。后续复查发现 E 组自己创建的权限延后保存链可在回合结束后写入，不能拿两次相同标签代表所有写者已结束；但原现场没有完整写前后戳，未将具体失效写者视为已证实，更不宣称修复生产 ETag 缺陷。现 E/D 保留原覆盖并新增磁盘头权限断言，H/F 使用同服务中没有中途权限修改的独立会话。原预算内必须拿到实际 304，异常状态或同标签 200 立即失败，采样变动即使最终通过也留诊断；B 与 F1/F2 的独立严格 304/不装载断言不变，失败保留 HOME。
- 第三轮完整回归为 522 通过、5 失败、0 flaky，残留测试浏览器 0。两件插话测试把 `live=true` 当成引擎已登记、可接收插话；新 live 覆盖启动与收尾所有权，这时 `queued` 是正确能力。现分别等待实际 `live && relay.channel==='steer'`，保留严格 steer、真实插话、零中断和落盘断言，不接受 queued 冒充通过。第二遍 `foreign-turn-busy-guard` 又暴露 C 组在启动阶段就发替代消息、却要求运行中 kill 审计的同类前置错误；该失败保留，新增独立 C1b 引擎登记断言，原 superseded 审计及胜者正文断言不变。
- 计划卡停止测试只认旧 live 卡的三枚禁用按钮，漏掉最终重绘成静态记录的合法形态。首次补测曾只认“已取消”，仍失败；保留该现场，检查真实合成会话 journal 确认停止会按 reject 结算审批，记录为 `source:'aborted'`、计划 `status:'rejected'`、`note:'turn stopped'`。最终仍要求唯一原计划：live 形态必须已决、失效且三按钮禁用；静态形态必须明确“已驳回”、停止原因精确匹配、正文仍为原计划且没有可操作控件，空按钮数组本身不能通过。
- 并发同会话的路径对比原来双发 `Promise.all`，没有控制第一回合是否已进入引擎：启动前被顶替可没有 result，进入引擎后被顶替会返回 aborted result。测试改用 Fake provider 会合，先确认第一请求真实进入模型并挂住，再发第二回合，严格比较相同抢占阶段的结果与胜者。
- 到访浏览器回归新增的路由覆盖未重算，导致第三轮路由清册静态件失败；已重新生成并校验。以上本轮收尾修订只涉及测试前置、判定及生成的覆盖清册，应用和桌面字节不变，实际 `31qc` 包的验收身份保持有效。

## 验证方法与证据边界

`release-package-acceptance.js` 直接解压两份实际 ZIP，校验整个 app 树及两种 EXE 与候选/构包 stage 的字节，检查随包 Node 和启动器文件。每种包分别用随包 Node 和 EXE 启动完全不存在的数据目录，执行真实 provider/tool 文件写入，并直接验证本片新增的 WebView 隐私边界，防止陈旧 EXE 靠相同版本号或工具数混过。桌面启动器另做实际窗口验收。

升级基线必须解析到实际 `v3.0.1` 标签的提交，由该标签源码通过 HTTP 和 Fake provider 产生配置、会话、provider 历史、用量及文件证据，再备份。两种候选包各用独立副本升级、重启、继续旧会话并再次重启，核对原配置、未知配置字段、会话及历史、完整用量行、记忆正文和原产物；最后用未动过的原备份交回旧标签源码验证恢复。这里验证的是标签源码运行产生的数据，不冒充下载的旧版发行二进制。

每种解压包还用原 runner 执行 15 项核心旅程：只读/派单、附件与搜索边界、交付、逐项待决、设置范围、多步骤、认可做法、主动记忆、发送中刷新恢复、交付浏览器及桌面内部数据保护，另加停止执行身份、会话 ETag、迟到到访和长文本收尾。先以随包 Node 硬检查构建新鲜度，再运行；禁止自动修包，并复核产物 hash，不接受隐藏重试。

Full 单独核对离线载荷完整性、第一次 `--ensure`、第二次幂等、无关 MCP 配置保留、安装版 Python 的模块来源与 WinSDK OCR。两个安装版 `python -I` MCP 入口实际握手、列出 108 工具并调用合成文件的 `file_info`，另跑随包 stdio smoke。

实际包验收和 `release-dryrun` 使用隔离数据目录、用户家、AppData、临时目录、工具箱、CLI 配置/历史目录及 ACC 安装目录，清除外部测试 server 与 Node/Python 注入。全量回归沿用公共夹具的逐件 HOME、合成 AppData 与浏览器 profile 作用域；旧夹具并非全部使用包验收的完整环境替换器。只回收自己持有的 ChildProcess 树。原用户窗口、配置和真实会话不作为可写测试夹具。

本次是当前 Windows 主机上的全新数据与升级副本验收，不等同于全新 Windows 镜像或缺少 WebView2/受组织策略限制机器的验收。真实模型语义证据沿用 79 号记录；本轮发布回归使用离线 Fake provider，7 项 live 仍独立按需执行。

## 用户走测反馈：多步骤交付与输入目标（31qc 之后）

2026-10-18 用户在 Full `31qc` 隔离走测副本完成“走测03-两步订单汇总”。只读核对原始 run、事件、工具记录与磁盘产物，并由独立 agent 交叉审计：同一 run 两节点，第二步依赖第一步；事件顺序为第一步启动、成功、第二步启动、成功、run 成功，第二步在第一步完成后 2ms 启动。两步均首次成功，未触发失败、等待或重试分支。步骤间结果消息真实送达；第二步仅一次文件写入，随后回读，父任务也完整回读且与磁盘一致。

`两步订单汇总.md` 为 1404 字节，SHA-256 为 `4675e64835673a5ed57c9c4a78964253ba13e72355c40324dbf44e825eea9561`。A/B 分别 2 条、1800/1200；销售与研发各 1500、总计 3000，A01/A02/B01/B02 完整。工具轨迹及 mtime 支持只改目标文件；没有运行前全目录 hash 清单，不宣称全树逐字节对照通过。

另记录语义体验问题：只读第一步把自己的工具限制误当成“第二步缺写工具”，进行了多余能力探测并声称后续受阻；实际 edit 第二步正常交付。这属于待优化的步骤角色理解，不把它记为调度失败或失败重试实测。

针对用户反馈的修订/新建冲突和交付卡小按钮过多，源码作如下后续修订：

- 交付卡默认只保留原轮摘要、“展开全文”主按钮和“继续修改”；短正文同样有全文入口。展开原地显示完整正文及产物细节，收起时版本、文件和检查一起收回；检查、刷新与工作台导航位于展开后的“更多”。接口刷新失败仍保留工作台入口，成功重试后归回更多，不复制导航节点。修订受阻或预检失败的反馈独立可见，不藏在收起的详情里；切换语言保持原展开状态。
- 主栏上限由 720 放到 900，头部、正文和输入共用居中列；消息不再额外卡在 680，用户气泡仍最多 520。窄窗口及右栏展开时，内容受可用宽度限制；主操作可以换行。
- 修订保留原任务和交付回合；普通 picker 和 Tab 不再静默移除修订来源。另起一件不覆盖当前修订，修订与取回草稿、外部参考也不覆盖已明选的新建目标。
- 修订和明选新建有独立原生取消按钮，保留文字、已传及在传附件；占位和提示一同复位。取消按钮只在对应状态出现，普通输入不增常驻操作。
- 用户明选 new 与自动预测 new 分开；在途预测不能覆盖明选，迟到发送回执也不能清掉下一份明选。空输入再输入仍保留用户明选，自动预测则继续随新文字变化。
