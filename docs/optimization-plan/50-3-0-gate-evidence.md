## §1 X02「管家 rules 进稳定层」——**前提不成立，明文关闭**（2026-09-20）

### 提议是什么

管家提示词分两层：**稳定层**（`pack.steward.stable`）进 `system`，**易变层**（记忆块、工作区表、
线程总览……）拼成第一条 user 消息的前缀。而 `rules`（行为纪律）**恒在、零条件**
（`13o:369` 是易变层的第一段），却待在易变层里 —— 原因写在 `06b` 的 rules 头注里：
**英文稳定层当年的【字符】预算塞不下**（「已到 2453/2500」）。

X02 的提议因此是：把 `rules` 挪进稳定层，好让它吃前缀缓存。

### 为什么它不成立

**前缀缓存断在「第一个变化的字节」，而那个位置在 `rules` 之后。** `rules` 是易变层的**第一段**
且逐字不变，所以它本来就落在两回合的公共前缀里 —— 挪不挪，它都已经被缓存了。

### 实测（真 API，`deepseek-flash`，本机端点）

同一条 system（stable）＋同一段 rules 前缀，连发几回合，只改 `rules` **之后**的内容
（模拟记忆块与总览每回合都变），看 `prompt_cache_hit_tokens` 够不够盖住 stable＋rules：

| | prompt | **hit** | miss |
|---|---|---|---|
| ① 冷 | 2375 | 512 | 1863 |
| ② 只改 rules 之后 | 2375 | **1280** | 1095 |
| ③ 同上，再来一次 | 2375 | **1280** | 1095 |
| ④ **对照：rules 开头改一个字** | 2376 | **640** | 1736 |

参考量：`stable` ≈ 718 tok、`stable + rules` ≈ 1386 tok（按 129a 那把尺子估；DeepSeek 按 **64 token**
分块，1280 = 20×64 是不超过实际边界的最大整块）。

**④ 是这份读数的骨头**：只把 `rules` 开头改一个字，命中就从 1280 **掉回 640**（≈ 只剩 stable）——
证明 1280 那一段**真的含着 rules**，而不是这把尺子在量别的东西。没有这一行，②③ 的数字说明不了任何事。

### 产线布局核对（不拿合成布局下结论）

上面的探针是合成的，所以另外核了真实装配：管家回合里 `09-workflow:1497` 把 `sys` 整个换成
`stewardPrompt.stable`，`turnVolatile` 就是 `stewardPrompt.volatile` —— 而它的第一段就是 `rules`
（`13o:369`），**中间没有任何会变的东西**。工具 schema 对管家回合是固定的 42 件，也不构成变化点。
第一个变化点是 `routeHintBlock` / 记忆块，两者都在 `rules` **之后**。

### 结论与代价

- **X02 关闭**：把 rules 挪进稳定层**省不下一分钱**，而且会把稳定层预算从 900 tok 撑到
  1386（中文）／1699（英文）—— **付出真实代价换一个零收益**。
- 顺带说明当年那个「字符预算塞不下」的约束**不必再解**：它挡住的那件事本来就没有价值。

### 这一趟真正量到的东西（比 X02 本身有用）

**每回合被重复付费的是 1095 token**（合成夹具上的读数），那是**记忆块 ＋ 工作区表 ＋ 线程总览**——
它们每回合都变，所以每回合都按未命中价重付。**X02 碰不到这一块**。

真正值得看的问题因此是：**这三块里有多少是「其实没变、只是位置往后挪了」的**。
按「变的排后面、不变的排前面」重排（例如记忆块把稳定条目排前、把本回合新增的排后），
能把断点往后推多少 —— **这正是 X01 `firstChangedSegment` 该照的地方**。
记在这里，等 X01 立项时直接接上，不必再摸一遍现场。

### 花费

本节全部真调用（含两次模型探路）**合计 6 次请求、不到 ¥0.05**（按仓里 `deepseek-v4-flash` 预置价
估算：输入 ¥1／百万、缓存输入 ¥0.02／百万、输出 ¥2／百万）。用户 2026-09-20 给的预算是 ¥80。

### 一个要记住的量具事实

`deepseek-flash` **是推理模型**：第一次探路给 `max_tokens: 16`，回答是**空串**，
16 个输出 token 全进了 `reasoning_tokens`。给到 800 之后才答出「收到」两个字，
而那两个字花了 **108 个 reasoning token**。
**以后任何用它做的评测：`max_tokens` 必须给够，空答复一律归 `empty` 不进分母**
（这正是记忆 `eval-instrument-bugs-first` 里记的那条，第一次探路就撞上了）。

## §2 X01「firstChangedSegment」——**问题已答，不建常设遥测**（2026-09-20）

### 它本来要回答什么

X01 在 35 号文里的定位是「**请求变化诊断**」：每回合的请求到底是**哪一段**变了。
它的价值不在自己，而在 §1 末尾提的那个问题：**每回合重复付费的那一堆里，有多少其实逐字没变、
只是排在断点后面**——那个数就是「重排能省多少」的上限。

**这一问不用建遥测也答得出来**：在进程内把真实的装配函数按真实入参调两次，量最长公共前缀即可。
本节就是这么做的，**零 API 花费**。

### 管家会话（`buildSystemPrompt`）

易变层 4 段：`rules` 668 ＋ 记忆块 449 ＋ 工作区表 91 ＋ 线程总览 385（稳定层 718 另算）。

| 情形 | 断点 | 命中 | 每回合重付 | 其中逐字没变、只是排在后面 |
|---|---|---|---|---|
| ① 一条线程状态变了（**最常见**） | 线程总览 | 1926 | 378 | **0** |
| ② 新写一条记忆 | 记忆块 | 1386 | 943 | 469 |
| ③ 工作区表变了 | 工作区表 | 1860 | 473 | 378 |

**① 是常态，可省 0** —— 现有顺序恰好就是「最不变的排最前」：rules（版本级常量）→ 记忆 → 工作区表 → 总览（每回合变）。

②③ 那两个「可省」数**不可当真**：它们成立的前提是「记忆变了但线程一条没动」「工作区表变了但线程一条没动」，
而真实回合里线程总览几乎总是跟着变。把 ②③ 的前提去掉之后，唯一真实可省的是
**把工作区表挪到记忆块之前**（记忆变、线程没动时省 91 tok），而它在情形 ③ 里反而多付 361 tok。
**净收益接近零，方向还不稳定。**

### 普通会话（`buildVolatileParts`）

易变层合计 1879 tok，其中**账本段只有 179 tok，其余 1700 tok（项目记忆＋技能索引＋工作台记忆索引＋playbook 索引）
会话内不变、全程命中**。

| 情形 | 命中 | 每回合重付 | 其中逐字没变、只是排在后面 |
|---|---|---|---|
| 账本里一个里程碑做完（每回合最常变的那一样） | 1750 | 129 | **96** |
| **对照：什么都没变** | 1879 | **0** | 0 |

**断点落在「`2/6 个里程碑`」那一行** —— `buildMissionPromptSection`（`06e:20`）把**进度计数排在里程碑清单之前**，
于是计数一变，后面整份清单（96 tok，逐字没变）跟着重付。

### 结论

- **X01 关闭：问题已答，不建常设遥测。** 两种会话的布局都已经接近「最不变的排最前」，
  重排的总可得空间是 **96 tok/回合（普通）** 与 **≈0（管家常态）**。按仓里预置价（输入 ¥1／百万）
  折算是 **¥0.0001／回合** 量级 —— 为它建一套长期运行的遥测设施，成本远大于它能省下的。
- **一处具体的小改动记在这里，但【不做】**：把 `mission.progress` 那一行挪到里程碑清单**之后**
  （或者干脆不印——它是可推导的），能让那 96 tok 留在缓存里。不做的理由：收益 ¥0.0001／回合，
  而它要动一段带快照锁的提示词、并可能改变模型对账本的读法。**这是一次取舍，不是遗漏。**
- §1 末尾提的那个问题到此有答案了：**那 1095 tok 里没有「白付的」，它们是真的变了。**

### 量具自己踩的两个坑（都记下来）

1. **按空行切段是错的**：`buildVolatileParts` 用**单个**换行拼（`06:1837`）。第一版按 `\n\n` 切，
   于是整层被报成「1 段」。改成直接量**最长公共前缀** —— 那本来就是前缀缓存的真判据，不需要知道段界。
2. **账本要的是 `milestones` 不是 `todos`**（`06e:13` 形状不对当场返回空串）。第一版传 `todos`，
   于是「改了账本」其实**一个字都没变**，断点报 −1 —— **读数看着合理，其实是假的**。
   现在每组都配一条「什么都不变 → 重付 0」的对照，这类假读数会当场露馅。
   同族的错在本波已经犯过多次，记忆 `reverse-check-can-be-wrong` 第六种说的就是它。

## §3 H02／H03「受管文件读版本登记与条件提交」——**证据收了，但它自己证不了自己**（2026-09-20）

### 证据门是怎么写的

35 号文：「受管文件读版本登记与条件提交**只在旧读痛点有数据后立项**」。
所以要回答的只有一句：**旧读痛点到底有没有真发生过？**

### 取证（本机真实会话历史，**只数不看**）

只取工具名与路径，不打印任何消息正文、参数正文或文件内容；样本里的路径只给哈希前 6 位。

**第一版的判据是错的，先说清楚**：我把「读过 X → 写 X → 没重读又写 X」当成旧读痛点，扫出 **655 次**。
但看样本就知道那是什么：`读@88 写@89 又写@90` —— **读一次、连着改几处，是标准编辑流程**，
不是痛点。**655 这个数不能当证据**，记在这里免得以后有人捡走它。

**换成可判的信号**：编辑**因为文件对不上而失败**的比率。

| 读数 | 值 |
|---|---|
| 扫过的会话 | 125 条 / 14734 次工具调用 |
| 写／改类调用 | **1606** 次 |
| 其中失败 | **150** 次（**9.3%**） |
| 失败里「`oldText` 对不上」 | **101** 次（占全部写改的 **6.3%**） |

### 结论：**这 101 次归不了因，而「归不了因」正是 H02 要修的那件事**

`oldText` 对不上至少有三个成因，**现有数据一个都分不开**：

1. 文件在读与写之间**被别人改了**（这才是 H02 瞄准的旧读痛点）；
2. 模型**记错了**原文（改述、凭印象写）；
3. **编码或空白差异** —— 仓里自己的诊断提示就点名了这一类
   （`12:717`：「oldText 含非 ASCII 字符……文件对应位置可能是 ASCII 形近字符，逐字节必然不匹配」），
   说明 ③ 在本仓是**已知常见**的。

**分不开的原因是：没有任何地方记下「读的时候这个文件是什么版本」。**
而那正是 H02 提议要加的东西 —— **证据门在这里是循环的：要证明该做 H02，先得有 H02 的一半。**

### 因此给出的结论是一个更小的下一步，不是 H02 本身

- **不立项 H02／H03 的完整形态**（受管资源的读写关联登记 ＋ 条件提交）：6.3% 的失败率**不足以**
  论证那么大的面，因为其中有多少是 ①，至今**没有一个数**。
- **该做的是把那 101 次归因**，而它只要 H02 的一个零头：**读文件时记下内容哈希，写的时候比一次**。
  失败信封里多一行「读的时候是 A，现在是 B」——于是 ① 与 ②③ 当场分开。
  这一步几乎不改架构，却能把这道证据门一次性收掉。
- **按用户定的口径**，本项目前状态是：**证据已收、结论是「按现有数据不立项」，并留下了一条
  成本极小的取证路径**。它不是「做完了」，也不是「没管」——是**有结论且结论可执行**。

### 取证脚本自己踩的坑（同一族，第三次）

会话消息里的键名是 **`toolCalls`（驼峰）**，不是 `tool_calls`。第一版按下划线写，扫出
「125 条会话 / **0 次**工具调用」—— **那是解析器没对上，不是没用过工具**。
`toolCalls[]` 的条目也不是 OpenAI 的 `{function:{name,arguments}}`，而是 `{id,name,input,result}`。
本波里同一族的错（夹具形状与产线对不上，读数看着合理其实是假的）已经犯到第三次，
都并进记忆 `reverse-check-can-be-wrong` 第六种。

### 6.2 离线升级与数据迁移恢复演练 ✅ **通过**（新增常驻件）

新增 `dev-harness/offline-upgrade-drill.e2e.js`（21 条）。**它补的是既有那几件都不管的那一层**：

> **没有一条断言看着「用户那一整个文件夹升级之后有没有少东西」** —— 而那正是升级事故的真实形状：
> 不是某个键错了，是某一类文件在新版本手里没人认领，悄悄被跳过。

| 段 | 演的是什么 | 结果 |
|---|---|---|
| (A)(B) 升级 | 造一个 `configSchema:11`、整份默认值冻在盘上、还带着当前版本**不认识的旧键**的数据目录，用当前构建读它 | 四条会话、五条管家记忆、六行用量台账**一条不少**；端点与密钥原样；schema 11 → 13；那三个被冻成 false 的开关**真的被迁移翻开**，而拍板不翻的两个**没被顺手带上** |
| (C) 降级兼容 | 新版写过盘之后，旧版本认识的键还在不在 | **不认识的旧键原样留在盘上**（47 号文 §4.2 第 24 条那一族的根治形状）。**自带尺子 C0**：先钉住「盘上那份确实被重写过（11→13）」—— 否则 C1 是白过的 |
| (D) 断电 | 消息 ndjson 与用量台账各追加一个「写到一半」的行 | 会话照常打开；**半行之前那两条完整消息读得出来**且是完整消息不是残骸；台账的半行不吃掉前面六行 |
| (E) 损坏隔离 | 把一个会话 json 写成坏 JSON | 它不让整份读取炸掉；**别的三条照常列得出来、逐条打得开** |
| (F) 备份恢复 | 整份拷走 → 删原件 → 拷回来 | 会话数一致，且每条的「上一句」**逐字一致** —— 备份是真能救回数据，不只是文件数对得上 |

**演练过程中把我自己的一个误判纠正了，值得记**：(D) 第一版报「半行之前的完整行 0 行」，
我差点当成「断电丢数据」这种重大缺陷。取证之后是**夹具自相矛盾**：我用 `appendFileSync` 直接往
ndjson 里塞行，而**会话头里记着 0 条**，于是一读就被对齐成 0 行。
「头是权威、文件向头对齐」**恰恰就是断电自愈的机制本身**（头说 N 行、文件有 N 行半 → 削掉半行）。
改成经 `saveSession` 的真路径造消息之后，(D) 三条全绿。
**本波同一族的错（夹具形状与产线对不上）这是第四次**，都并进记忆 `reverse-check-can-be-wrong` 第六种。
