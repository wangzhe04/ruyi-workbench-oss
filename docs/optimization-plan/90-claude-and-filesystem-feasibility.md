# 90 · Claude 网关、严格文件边界与进程回收调查

> 2026-10-21。承接 [89 号续验](89-audio-and-cli-isolation-followup.md)，实验基线 `3fea5af1`。本轮只验证两个剩余技术难点并调查既有测试失败；ASR 保持暂缓，应用版本与 3.1 发布门不变。

## 严格文件隔离：当前 LPAC 方案未通过

合同要求宿主原值文件位于托管进程可见范围之外，不依赖这些文件恰好采用普通用户 ACL。可见范围须明确列出模型投影、输出/home/cache、必需系统运行资源及容器自有存储。限定负例不能证明整个文件系统已被枚举或隔离。详见[实验合同](../../dev-harness/privacy-m1/cli/filesystem-contract.md)、[观察说明](../../dev-harness/privacy-m1/cli/filesystem-findings.md)及[入库证据](evidence/privacy-m1-cli-filesystem.json)。

| 自有合成目标 | LPAC + registryRead 的父/子进程观察 |
|---|---|
| 投影文件与输出目录 | 投影可读不可写，输出可写 |
| 投影外普通用户、Everyone、AAP 授权目录 | 读取、枚举、写入拒绝 |
| 投影外 ARAP 授权目录 | 读取、枚举、扩展路径读取成功；可写且带低完整性标签的目标写入成功 |
| 投影外目标 profile SID 授权目录 | 同样可按其授权读取、枚举和写入 |
| 新建 profile 的自有存储 | 父子均可读、枚举和写入，必须另列授权面 |

九个投影外 fixture 在宿主均有读/枚举/写正控制。父子矩阵完整，ARAP 与 profile 共 28 项越界成功观察。ARAP 反例已经否定严格路径白名单合同；它不表示所有真实宿主文件都可读，也不依赖其他测试是否正常退出。

额外受限 primary token 使用 `CreateRestrictedToken`、`DISABLE_MAX_PRIVILEGE`（保留 `SeChangeNotifyPrivilege`）、单一随机 restricting SID，再经 `CreateProcessAsUserW` 与同一 LPAC 属性启动。挂起进程实际 token 中恰有预期的一项限制 SID，随后 Node 在执行 JS 之前以 `0xc0000022` 退出，没有后代和探针输出。该候选尚不可用；具体缺失资源未定位，不能把零输出当作保护通过。本轮没有为它修改既有系统/用户目录 ACL 或启用特权。

路径别名单列：父子四次实际 junction 创建均为 `EPERM`，之后的 `ENOENT` 不能证明别名目标被隔离。故意制作的投影硬链接与投影外文件共享身份，投影继承授权改变了同一文件的 ACL，父子随后均能从外部名称读取。这个结果说明投影制作器也必须拒绝重解析点和多链接文件；它不是另一种 token 授权结论。独立审查还发现 fixture ACL 校验本身未检查硬链接，已补齐原生链接数检查；两个自有临时根之间的硬链接负例被拒绝，sentinel 未改变。

两份实际后代 token snapshot 与根进程 package/capability 一致，但两个 C# TokenProbe 都在输出后以 CLR `0xe0434352` 退出。证据保持 `descendantTokenProbeCleanExits: false`、`infrastructurePassed: false`，runner 退出 1；先前两次管道捕获超时与首次 CLR 失败也保留，具体原因仍未知。两次最终启动的 Job、profile 与临时目录清理均核验成功。不能将这一轮写成“全部通过”。

独立代理再次运行同一 OS 实验，复现上述 ARAP 反例、CLR 失败和额外 SID 的启动阻断。七份显式源码 manifest 为 `291d6ce81b7b153e4c3911175f52073df37ce9a46b36931eb1d6dd40fe20fcfb`，与当前源码及两份报告一致；依赖哈希匹配。独立结果 SHA-256 为 `4b253b91e0faad0fe6ef99f620af7271e617be2deec05ad0cf64cf5da66717c4`，归档在仓库外维护目录 `checks/m1-filesystem-review/`。

设计裁决：LPAC 可以继续作为能力受限的实验层，当前实现不能承担“严格宿主文件视图”的产品承诺。下一条方案要先验证独立文件命名空间或其他 OS 强制机制，再接 CLI 工具链。VM/Windows Sandbox 只映射明确投影、关闭不需要的共享与网络，属于候选设计；普通 WSL 关闭自动挂载仍不足以排除手动挂载和其他宿主通道。本轮未安装或启用这些环境，也没有证明其他全部 Windows 方案都不可能。

下一原型的最小合同先固定为：宿主原项目不映射，guest 只取得只读模型投影和有界输出；关闭剪贴板、宿主磁盘、interop 与共享凭据等额外通道；模型请求只能进入固定接收方的宿主 broker，原值工具处理留在宿主权限边界；guest 内任意代码及后代仍不能访问宿主 ARAP/普通用户合成秘密或自行挂载宿主目录；重启、取消、崩溃和共享目录路径替换都有实际负例。guest 自有系统资源与宿主文件权限分开清点，不能把普通虚拟机启动或关闭自动挂载等同于此合同已通过。

本机只读前提检查仅观察到 `HypervisorPresent: true`，未发现 `WindowsSandbox.exe`；可选组件状态查询返回 COMException，状态未知。它不足以确认 Sandbox 已可用，本轮没有修改 Windows 功能。候选的最低系统条件、离线组件来源与分发许可仍需另行冻结，不因此缩小 86 中的发布验收要求。

## Claude：先分开启动、路径兼容和模型传输

安装程序冻结为 Claude 2.1.202，完整程序副本仅用于自有临时环境。版本输出、Bun 运行时标记、管道连通、模型提交、助手完成分别判断。`BUN_BE_BUN` 即使成功也会替换应用入口，不能作为 Claude 模型证据。

初轮带引号绝对路径的 `BUN_OPTIONS` 未到预加载；相对路径预加载可实际执行 Bun 1.4.0。专用 LOCAL 管道连接成功，但 NUL stdin、公开 bare/配置隔离选项仍未使模型调用发生；宿主假 provider 正控制成功、模型请求零次不能证明外发保护成功。

有界诊断进一步观察到：existing 祖先目录的 metadata 操作为 `EPERM`；投影/home/入口的 stat 成功，普通 `realpathSync` 为 `EPERM`，公开 `realpathSync.native` 实际解析成功。扩展路径和 preserve-symlinks 选项没有消除该差异。诊断只保存封闭操作/错误枚举、路径分类及哈希，不保存原路径、内容或堆栈；同进程诊断仅作排查线索，不是可信控制回执。

当前兼容候选仅对宿主冻结的自有投影范围，在普通同步解析报权限错误时调用真实 `.native`，检查原生解析结果仍属于该范围；保留外部路径、非法输入和其他错误的原行为。普通与 native 接口的符号链接等语义有差异，因此这是冻结运行时的兼容层，不能宣称 API 完全等义，更不承担文件安全边界。没有采用伪造路径返回、DOS 盘符映射或系统 ACL 放行。

最终结果：两次真实原生模型尝试均连接了 LOCAL 管道，但模型请求为零、退出 124，未观察到助手或成功 result。后一次兼容层诊断实际记录到应用调用普通 `realpathSync` 失败、转入真实 `.native` 成功，随后同次应用 `realpathSync` 返回成功；之后没有其他可见 FS 操作或 event-loop tick，仍在 15 秒超时。因此首个兼容障碍已跨过，剩余初始化原因未知。不能把这个结果推广为完整初始化已修复或模型网关已经可用。

Bun 1.4.0 的实值回执还表明：兼容层安装成功、公开 `syncBuiltinESMExports` 调用返回、require 引用匹配，但先前捕获的 named binding 不匹配；Node 的对应单测通过不能代替 Bun 行为。未继续构建模块代理或大范围替换文件 API。宿主固定 Anthropic schema 的 PrivacyCore/协议适配帧/假接收端单测通过，只证明该独立合同；真实 Claude 的模型门仍未通过。

后续优先把官方 HTTP 网关放进新的受限资源环境验证，减少对 Bun 内建模块引用方式的依赖。这个兼容层保留为实验与复现材料；严格文件合同尚不成立时，不通过扩大文件 API 包装、开放通用网络能力或延长超时来开放产品支持。

[Claude 入库证据](evidence/privacy-m1-cli-claude.json)保留七轮、15 次启动的历史及其各自源码身份，清理均核验成功；最后一轮是诊断，不取代历史模型失败。最终 23 项显式源码/合同 manifest 为 `064889b02be7858cb15645ad2d4201337428c1224501cf59f1f2c529c6e4959e`，与当前文件一致，原/副本各含 11 个程序文件，整树哈希一致。24 项 CLI unit 通过，独立审查覆盖其中 16 项相关单测，并只重跑最后一次诊断：复现实际 native 跨过首个解析、后续超时与清理完成，模型结论仍失败。独立报告 SHA-256 为 `94fedcfde88c4cb58a98fe5cedc39c1e006d96fa264e015ea62e19408c212066`。

## 进程回收：首次根因仍未确定，补齐可区分的观测

原全量结果保留：2500 项中 2473 通过、26 跳过，R1b 一次失败。原日志只保存“某 PID 在 300ms 后仍存在”，没有清理回执及创建时间，无法事后区分同一进程仍活、PID 复用或其他观测问题。[调查汇总](evidence/kill-own-tree-r1b-investigation.json)记录 8 轮平稳、12 轮四路自有短进程 churn、1 轮脚本校验，共 21 轮未复现；不是首次原因已查明或已根治的证明。

确认并修正了测试的四个缺口：只按 PID 判断身份、将快照失败当成退出、丢弃清理回执、stdout 数字未到完整行就接受为 PID。现在捕获 PID 与创建时间，快照失败明确红灯，失败信息保留前后身份、清理回执及根退出字段。300ms 主判据不变，`kill-own-tree.js` 实现未改。新增真实 detached 孙进程负控证明“只杀根”的坏实现仍会被拒绝。

失败收尾显式持有原生 Process handle，再核创建时间并终止，只处理捕获的自有身份；之后再次核验这些身份已经消失。原断言失败时附加清理错误，不覆盖首次错误。诊断脚本单列 `cleanupVerified/cleanupError` 并在失败时退出非零。实现及独立最终复验均为 7/7 unit 通过；历史 21 轮在这些最后收尾改进之前，原始结果和缺失的旧脚本完整哈希不作追认。

该改进提交为 `4293b5da`。三份原始报告及手工汇总在仓库外维护目录 `checks/kill-own-tree-r1b-3fea5af1/`，首次失败没有改记为通过。

为复查完整并发背景，收尾另以原 unit 门的 4 路预算直接运行全部 root unit：[复查记录](evidence/kill-own-tree-r1b-full-unit-recheck.json)为 2502 项、2476 通过、26 跳过、零失败，295.5 秒；R1b 与真实残留负控均通过，仍未复现首次失败。报告绑定 279 份 unit 清单及当前测试/清理器/诊断脚本哈希，原日志另存 `checks/m1-r1b-full-unit-recheck/`。这是单独的 unit 重跑，没有重跑 run-all 全局准备、静态阶段或全量 E2E，不宣称原 fast 整轮已全绿，也不以这次通过推断首次根因。若未来再现，新回执可明确区分真实残留与观测失败。
