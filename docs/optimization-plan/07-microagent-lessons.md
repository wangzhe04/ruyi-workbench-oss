# 07 · MicroAgent 论文对照与编排方法论升级规划

> 基线：论文《MicroAgent: Context-Augmented Multi-Agent Framework for Automatic Microservice Decomposition》（arXiv:2606.29742v1，CUHK + 中山大学，2026-06）× Ruyi 现状对照（2026-08-10，主会话亲自工具核查，未用子代理报告）。
> 行号对应核查时的 `app/src/*.js` 当前版本，改动后会漂移，请以就近搜索为准。
> 性质：只读对照分析 + 候选优化项，未改动任何现有代码；定位为 06（HB360 成本收敛）的姊妹篇——06 治「单 agent 烧 token」，本文治「编排层的方法论沉淀」。

---

## 0. 一句话结论

Ruyi 的大方向（多代理分工 / 终局验证 / 上下文压缩）与论文一致，论文 RQ3 消融反过来给了 Ruyi 学术背书；真正差距在三点——**编排上下文只有「时间维度」压缩、没有「空间维度」分级**（所有节点共享一份 4000 字符 `contextText`）；**方法论只写在 prompt 里、没有沉淀进工具**；**确定性节点只有 vote/dedupe 两种 verdict 聚合，没有通用结构计算，且 vote 门有误杀正确结果的前科**。三点与 06 文档的 O4/O6 和 HB360 成本问题直接叠加，建议作为候选波次并入 roadmap，不抢占 3.0 收口。

## 1. 论文机制速览

MicroAgent 把「单体应用拆微服务」拆成 5 个子任务（领域识别 → 按领域动态实例化聚类 agent → 领域合并 → 公共类分配 → Review agent 终局兜底），三个核心机制：

| 机制 | 内容 | 论文证据 |
|---|---|---|
| 多粒度上下文 | 同一份代码库按三档粒度暴露：应用级（包/类清单 + DB 摘要）、类级（LLM 类摘要 + JSON 基本信息）、依赖图（AST 静态分析）；不同 agent 只拿自己需要的粒度 | 消融：去掉依赖上下文显著掉分 |
| 两类工具 | 通用检索工具 + **把方法论编码进去的专门工具**（语义搜索、依赖熵排序、拓扑排序传播分配）；结构性计算交给确定性算法，LLM 只做语义判断 | 消融：聚类工具、公共类工具各有实质贡献 |
| Review 终局兜底 | 不只是质量判断，还显式处理**未分配项**，保证输入集合被穷尽覆盖 | 公共类分配 F1 93.4%（超基线 41.1%） |

关键结果：平均拆分准确率 89.2%（超 SOTA 24.6%）；**消融中贡献最大的是多代理工作流本身**（去掉后 WS 掉 13.8%，F1 掉到 81.2%），其次是专门工具与依赖上下文。动机例子：裸 LLM 会幻觉不存在的类名、按「名称相似」而非「代码级使用证据」分配类。

## 3. 优化项矩阵

## 4. 各项详细方案

### M1｜编排上下文分级注入（P0）

**问题**：`09-workflow.js:647` 把 `contextText` 截 4000 字符后拼进**每个节点**的 prompt——领域识别节点和终局 verify 节点拿到的是同一份。论文证明「按角色暴露不同粒度」对准确率有实质贡献；对 Ruyi 则直接省 token（06-O6 做了子代理**工具**最小集，**上下文**最小集还没有）。

**方案**：`runAgentWorkflow` 的 `contextText` 保留为**全局层**（所有节点可见）；节点定义新增可选 `context` 字段为**节点层**（仅该节点可见，追加在全局层之后）。模板编排器按阶段填不同粒度：探索节点给结构摘要，执行节点给具体片段，verify 节点给产物清单 + 原始要求。

**代码切入点**：
- `09-workflow.js:647`（contextPrefix 构造处）——改为 `全局层 + (node.context ? 节点层 : '')`
- `13-http-router.js:1884` 附近节点 schema——加 `context: { type: 'string' }`
- 模板定义（`orchestrate_agents` 工作流模板注册处）——8 个模板逐步回填分级内容

**兼容**：节点无 `context` 字段时行为与现状完全一致（只发全局层），旧模板零迁移。

**预期**：长编排（deep-research / codebase-audit 类 10+ 节点）input tokens ↓15-30%；子代理因上下文聚焦减少「看错题」类失败。

**验收**：HB360 中编排类任务子集回测（token 对比 + outcome 不退）；新增 e2e：节点层 context 只出现在目标节点的请求体（fake-openai 落盘断言）。

**风险与缓解**：模板作者把大段内容塞进节点层反而更烧 → 节点层同样过 4000 字符截断闸 + 文档注明「节点层只放指针/摘要，不放全文」。

---

### M2｜确定性节点扩展 + vote 门防误杀（P1）

**现状**（已核实）：vote/dedupe 已是确定性聚合（`13-http-router.js:1884` 注明「do not execute task」），但能力仅限聚合上游 verdict+confidence。论文的公共类分配用**拓扑排序传播**——结构性工作不过 LLM。

**方案两半**：
1. **vote 门防误杀**：阈值/置信口径可配（节点级 `gate.threshold`），低置信票记「弃权」而非「反对」；默认行为不变。对症记忆中「vote 门误杀正确结果」。
2. **确定性节点扩展**：在 vote/dedupe 之外新增内置集合运算节点（初版两个够用）：`coverage`（输入集合 vs 各节点产出的覆盖率统计，输出未覆盖项清单——正好是 M3 的机器数据源）、`propagate`（按依赖边传播赋值，论文拓扑传播的通用化）。

**代码切入点**：`08-agent-runs.js:1683`（deterministic_gate 判定）、`09-workflow.js:655`（vote 聚合处）、`13d-core-domain-routes.js:128`（deterministic 标记）。

**验收**：vote 弃权语义 e2e（低置信不再否决）；coverage 节点对构造输入输出正确未覆盖清单；编排盲区补测沿用第46波纪律。

**风险与缓解**：新节点 kind 扩散 → 初版只做这两个，其余需求先以子代理 + 脚本顶。

---

### M3｜verify 节点加「输入覆盖率」职责（P1，纯 prompt 层）

**问题**：论文 Review agent 的核心价值是处理**未分配项**（unassigned classes），不只是质量判断。Ruyi 的 verify/review 门（`09-workflow.js:617-618` 的 `QUALITY_GATE_OUTPUT_SCHEMA`）只问「好不好」，不问「全不全」——正是 06 文档「细节精度失守——产物框架对、关键 check 挂掉」的编排层对应。

**方案**：质量门 schema 与 prompt 增加 coverage 维度：要求 verify 节点输出「输入项总数 / 已处理数 / 未处理项清单」，未处理项非空时门不通过（或按模板配置降级为警告）。

**代码切入点**：`09-workflow.js:617-618`（QUALITY_GATE_OUTPUT_SCHEMA 与 qualityInstruction 构造）。

**预期**：codebase-audit / data-insights 类模板的漏项率下降；与 06-O3（单 agent 逐项自检）形成「单 agent 查产物、编排层查分工」的双层覆盖。

**风险与缓解**：prompt 改动走第51波护栏（快照测试 + fake 落盘断言）；verify 节点本身可能幻觉 coverage 数字 → 有 M2 的 coverage 节点后切换为机器数据，prompt 版作为先行。

---

### M4｜HB360 单轴消融评测纪律（P1，流程项）

**问题**：06 文档 §7 自认数据局限；O1–O6 若多项同上，token/outcome 变化无法归因。论文按「工作流 / 工具 / 上下文」三轴消融，是可直接抄的评测设计。

**方案**：06 各项落地时强制「单轴开关」——每个优化项必须有独立 runtime 开关，回测时只开这一项对比基线，再开全量对比。归因轴对齐论文三轴：工作流（编排结构）/ 工具（注入集）/ 上下文（压缩与注入）。

**预期**：每项优化的真实收益可量化，避免「打包上线后不知道哪项有用」；为后续写 Ruyi 自己的技术报告积累可引用数据。

---

### M5｜高频模板配「方法论工具」（P2）

**问题**：论文消融显示专门工具（依赖熵排序、拓扑传播）是独立贡献因子；Ruyi 的方法论全部写在模板 prompt 文本里，靠模型自觉执行。

**方案**：按模板使用频率逐个配确定性辅助工具，候选：
- codebase-audit → 符号/引用检索工具（文件级依赖图，证据优先于名称相似——论文动机例子的正面解）
- debug-root-cause → 二分复现记录器（假设/实验/证伪状态机落盘，防 loop 早停）
- data-insights → 数据画像摘要工具（行数/分布/异常值机器统计，替代 LLM 目测）

**纪律**：过第49波新工具入库全部门（契约 + fake 回归 + description 审计）；一次只做一个，用 M4 消融验证收益再做下一个。

---

### M6｜O3 自检升级为「证据回溯」（并入 06-O3）

论文 case study 的关键是「按代码级使用证据分配，而非名称相似」。06-O3（产物落盘前逐项自检）升级：自检不只查「产物存在 / 覆盖要求项」，还查「产物中的关键断言能回溯到证据」（文件引用、命令输出、数据行）。不单独成项，作为 06-O3 实施时的验收标准补充。

## 6. 与既有规划的衔接

- **06（HB360 成本收敛）**：M1 是 O6 的同构补全（工具最小集 → 上下文最小集）；M3 是 O3 的编排层对应；M4 是 06 全篇的评测前置；M6 并入 O3。建议 06 第 2–3 波实施时同步采用 M4 纪律。
- **编排可靠性前科**（vote 误杀 / loop 早停 / probe 精确率 ~60%）：M2 直接对症 vote 项；loop 早停项由 M5 的二分复现记录器候选覆盖。
- **第51波提示词护栏**：M3 属 prompt 改动，必须过快照门，不得绕。
- **Pretender 3.0 收口**：本规划全部候选波次排在 3.0 默认切换之后，不稀释收口资源。

## 7. 不宜照搬的部分（诚实性）

- 论文是**单领域纵深系统**（Java 微服务拆分，目标服务数已知），Ruyi 是通用工作台——不把 DDD 五阶段硬编码进引擎，只把「阶段化 + 专门工具 + 分级上下文」抽象为模板可表达的通用能力。
- 论文的依赖图来自 JavaParser AST 静态分析；Ruyi 面对的是任意语言/任意任务，M5 的符号检索工具初版只能是「够用」级（grep/ctags 级），不承诺论文级精度。
- 论文评测基于 10 个 Java 应用与 3 个模型 backbone，其消融结论（各因子贡献排序）在 Ruyi 场景未必同序——M4 存在的意义正是用 Ruyi 自己的数据重排一次，而非直接采信论文排序。
