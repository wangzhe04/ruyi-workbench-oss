# 88 · M1 外发边界与本地处理原型

> 2026-10-21。范围来自 [86 号路线](86-3.1-completion-and-privacy-roadmap.md)。本文记录设计、可重复实验和未解决条件；原型位于 `dev-harness/privacy-m1/`，不接入生产发送路径，不代表 3.1 可以发布。

本文保留首轮原型及发现时的事实。后续音频生产修复、LPAC 续验和 ASR 可选范围调整见 [89 号记录](89-audio-and-cli-isolation-followup.md)。

## 1. 本轮要回答的问题

1. 当前第一方代码有哪些能够把内容交给网络、外部进程、浏览器、MCP 或导出文件的通道？每个通道由谁决定接收方和用途，现有保护位于哪里？
2. Windows 能否在不改变全局防火墙、不读取用户配置的条件下，限制整个 Claude/Kimi 进程树，并提供受控的模型与工具桥接？
3. 现有本机组件能否把图像中的敏感文字真正从像素及元数据中移除，且实际上传的仅是处理后字节？音视频离线处理还缺哪些组件？

M1 不使用真实秘密、真实账号或用户媒体。实验中的公开文字和秘密均为合成数据。以独立接收端、文件系统观察及实际 OCR 结果为证据，不能以模型回答或源码关键字数量替代行为断言。

## 2. 外发合同

生产阶段需要统一的调用合同，但本轮先核对事实，不提前创建庞大的抽象框架。

| 字段 | 必须回答的问题 |
|---|---|
| recipient | 实际最终接收者是谁？主机、端口、协议与重定向变化是否重新检查？ |
| purpose | 是模型推理、业务调用、本人本地导出，还是远程回复？同一数据在不同用途下不能自动复用批准。 |
| payload | 正文、资源、文件名、头、错误、媒体原件及元数据分别是什么？ |
| source | 内容来自哪个只读快照、会话与版本？派生物是否绑定原件、规则和处理器版本？ |
| authority | 调用者原有权限是什么？隐私代号的还原不提供新增权限。 |
| decision | 放行何种投影、拒绝原因是什么？策略改变或目标改变后是否失效？ |

清册将网络调用、委托执行和本地导出区分，不能把每个文件写入都称为网络泄漏。生成的逐点索引用于复核；保护程度需有人读过调用链的证据。词法扫描、别名追踪和源文件指纹只是漏项/变更提醒，不能证明所有动态执行或第三方内部行为均已覆盖。生产发送断言与该清册承担不同职责。

## 3. CLI 隔离设计与出门门槛

先验证零网络 capability 的 Windows AppContainer，宿主仅投影必要程序资源、合成项目以及专属可写目录。进程树必须继承边界；Job Object 仅负责生命周期，不能作为安全隔离证据。配置、缓存、HOME、TEMP 和环境变量使用隔离值。

普通 AppContainer 会获得部分 `ALL APPLICATION PACKAGES` 资源访问权，不能先验地当成独占文件白名单。本轮增设投影外自有合成文件的该权限负控；如果仍可读，模型视图隔离就未成立。下一片需验证 LPAC 的权限收缩与运行时兼容性，不能通过修改用户原始目录权限来掩盖问题。机制依据见 [Microsoft AppContainer 与 LPAC 启动说明](https://learn.microsoft.com/en-us/windows/win32/secauthz/implementing-an-appcontainer)。

宿主 broker 应在边界外完成原值操作，只向 CLI 提供当前调用获准的模型视图。stdio/本地 IPC 只能提供有界、结构化操作，不能接受任意命令、路径或任意目标 URL。固定内容的模拟 RPC 仅验证 IPC 可用性，不能证明官方 CLI 已接入 broker。

| 层次 | 必须取得的证据 |
|---|---|
| OS 原型 | 允许的读取/写入成功；边界外合成秘密不可读写；子进程具有同一限制；独立 TCP4/6、UDP4/6 接收器正控制成功、未授权探测零接收。 |
| 组件运行 | 固定实际 Claude/Kimi 程序版本和入口哈希，在同一边界启动；记录失败诊断，不能退回边界外运行来取得通过。 |
| 真实闭环 | 每个实际 CLI 至少一条模型请求、工具调用、编辑及结果回到模型的路径经过保护边界；模拟服务证据与真实服务证据分开。 |
| 完整支持 | 后续 M4 覆盖压缩、继续、重启、缓存、配置注入、hooks/plugins/MCP、子进程及更多网络旁路。 |

只通过前两层不能关闭 M1。若零网络环境无法访问独立宿主 HTTP gateway，下一步是验证官方可支持的传输/进程内适配或重新设计隔离服务，不添加全局 loopback 豁免，也不放开网络后沿用“已隔离”结论。实际 DNS 解析、公共网络和局域网未测时必须单列，向自建 UDP 端口发 DNS 格式数据不能替代系统解析器测试。

参考：[Microsoft AppContainer 隔离](https://learn.microsoft.com/en-us/windows/win32/secauthz/appcontainer-isolation)、[Windows 网络隔离与 loopback](https://learn.microsoft.com/en-us/windows/security/operating-system-security/network-security/windows-firewall/troubleshooting-uwp-firewall)。官方 Claude 的 shell sandbox 覆盖范围与 Windows 限制见 [Claude sandboxing](https://code.claude.com/docs/en/sandboxing)，不能替代整进程隔离。

## 4. 媒体设计与出门门槛

图像路径固定为：原件字节快照 → 本地 OCR 文字与坐标 → 现有 PrivacyCore 规则区间 → 全部相交词框像素遮盖 → 全新像素容器编码并去元数据 → 再识别及字节验证 → 仅上传派生件。跨词规则按完整区间处理，不只遮一个词；所有坐标需处于实际图像边界内。

来源、规则、处理器和派生物均记录哈希。提交前取消、超时、组件缺失、无法识别或验证失败均停止发送；没有原件回退。已提交后的取消/超时只终止当前请求，标记结果未知，不能声称撤回已发字节或自动重试。实际接收端捕获派生字节并核对哈希，保留公开信息的断言与秘密不可识别的断言同时成立。二次 OCR 与黑色像素检查仍不能证明任意图像内容都被识别，原型支持范围必须写明字体、语言、旋转和缩放条件。

策略由独立 owner 提供当前 revision/hash，旧 detector 不能自行宣布自己仍是当前策略。处理结束及 HTTP 提交点均核对权威版本；上传端接收取消信号和绝对期限。替换策略对象与原地修改策略都需使旧处理失效。

图片成功不代表 PDF/Office 的隐藏文字、附件、缩略图和修订历史已覆盖。音频先考虑离线 ASR 后发送保护文字；视频先考虑明确支持的文字派生路径。没有本地模型/解码组件就记录缺口，不下载替代依赖、不使用云端回退，也不声称抽查帧即已清理完整视频。

## 5. 证据与维护

实验结果使用 `passed`、`failed`、`blocked`、`missing`、`untested` 分别表达，禁止将后三者计入通过。脚本记录操作系统、运行时、实际组件版本、源哈希和清理结果，重跑不覆盖首次失败的含义。临时程序与合成媒体不入库，仓库仅保存源码及不含原始秘密的汇总。

三个原型分别在 `egress/`、`cli/`、`media/` 下维护；顶层 README 是唯一运行入口。结果由主代理审查，并由独立代理复核相关边界，再决定后续生产接入。M1 未达出门条件时，86 的 M2–M6 发布承诺不因“原型已提交”自动完成。

## 6. 本轮结果

整理提交为 `f5006d51`。本轮随后实现三个相互独立的原型，应用仍为 3.0.1，生产行为未修改。主代理负责合同与整体验收，6.1 Sol 分工实现，另由非实现代理独立审查。

### 外发清册

入口为[生成清册](../architecture/privacy-egress-inventory.md)和[源码审计说明](../../dev-harness/privacy-m1/egress/AUDIT.md)。首版清点 267 份第一方源码与声明配置、653 条候选，覆盖模型、Web、MCP、CLI、机器人、ACC、导出与媒体等能力；候选含本地操作、同名误报与动态未知项，不能视为 653 个外网出口。任何通道都没有因本轮扫描被升级为 `protected`。13 项清点器测试及生成物新鲜度检查通过，两项独立审查问题修正后复核通过。

审查发现工作台自身独立 MCP 的 stdout 出口原先遗漏，与宿主受管 MCP、独立 ACC 应分开登记。另发现现有 `transcribeAudioViaProvider` 在入口检查媒体策略之后，可能等待 toolbox 初始化及重新读配置，再发送原音频。合成调度复现了入口 off、等待期间切 basic、发送时仍含原音频的窗口。**本轮仅登记事实，生产漏洞尚未修复**；在发送提交点重新核验权威策略属于后续生产接入的优先项，不得沿用无条件 `blocked` 结论。

### CLI 实验

[CLI 说明](../../dev-harness/privacy-m1/cli/README.md)、[原始失败记录](../../dev-harness/privacy-m1/cli/prior-attempts.json)、[本次证据](evidence/privacy-m1-cli.json)。本机 Node 24 与 Windows 实测：

- 父/子进程获准读写成功，普通投影外合成文件读写被拒绝；实际后代 token 确认 AppContainer。固定 stdio broker 仅验证协议原型。
- 六个独立接收端各有一次成功正控制；隔离内父/子 TCP4/6、UDP4/6、私有网关和自建 DNS 报文探测没有到达接收端。超时/无回复如实保留，系统 DNS、公网及局域网未测。
- **父/子均能读投影外授予 ALL APPLICATION PACKAGES 权限的合成文件**。普通 AppContainer 的严格文件视图假设未通过。
- 实际 Claude 2.1.202 的 version 成功，help 与合成 prompt 超时无输出；Kimi 0.42.0 的 version/help 成功，实际 prompt 进入回合后 API 重试超时。两者私有网关正控制正常，隔离请求零连接/零模型请求。没有一条真实 CLI 模型/工具闭环通过。
- 八次启动均有清理回执，profile 删除成功、目录消失、Job 活进程清零。额外挂起父/子测试证明超时回收；机器断电后的恢复未测。

因此证据是 `infrastructurePassed: true`、`completedM1: false`。现有网络约束与文件视图尚不能提供可用的托管 CLI 支持。

五项 runner 单测通过，独立代理复核源码、绑定哈希和证据未发现新的原型阻断问题；没有另跑 OS 实验。当前入口哈希只绑定入口文件，不能代表完整 Kimi 依赖树，后续冻结还需记录依赖树及 Node 运行器哈希。

### 本地媒体

[媒体说明](../../dev-harness/privacy-m1/media/README.md)、[本次证据](evidence/privacy-m1-media.json)。三张真实 OCR 合成图（普通、缩放、EXIF 旋转恢复）完成真实规则识别、跨词全区间遮盖、去元数据、公开文字保留和实际 HTTP 字节验收。16 项拒绝负例零外发；另两项在派生字节已到达后取消/超时，正确标为未知。接收端总计五份派生件，三份确认、两份未知，原件零份。

独立审查发现并修复策略对象替换不失效、上传阶段缺取消/期限两个问题，再次独立复验通过。三项映射单测与 E2E 通过，源码哈希与证据匹配，合成媒体及临时目录清理完成。

这只证明限定英文 PNG 夹具路径。所检查运行时缺少 ASR 包及已配置模型，PATH 未发现 ffmpeg/ffprobe；完整转写、视频、PDF/Office、多语言与任意图像安全门均未完成。音频的拒绝测试不计作转写成功。

## 7. 下一片实施顺序

1. 修复已发现的原音频策略变更窗口，使用实际生产入口和合成接收端验证 off→basic、取消与等待初始化后的发送行为。同步复核实时音频连接及各发送提交点；不靠追加零散入口检查替代权威策略版本。
2. 继续 M1 的 CLI 路线裁决：LPAC 文件负控、运行时兼容性、受限 IPC 与官方 CLI 模型传输的适配可行性。必须同时满足严格文件视图与可用网关，不能只解决其中一个。无法成立时重新设计并保留 blocker。
3. 冻结本地 ASR 适配器/模型/许可证/离线体积及目标机器预算，再做实际音频→文字→保护→接收端闭环；图像扩大到中文、低质量、截断、未知识别结果与资源预算。
4. 上述 M1 条件满足后再把外发合同接入生产 M2；现有完整 M1 出门条件未降低，M6 发布仍未开放。
