# 3.1 递话失败与迟到响应的保护

设计日期：2026-10-17。基线：`18a2b11e`；实施分支：`codex/steward-3x-implementation`；当前应用版本 3.0.1。承接 [62 号方案](62-steward-3x-iterations.md) 第三轮 P1 第二片（「失败和迟到响应保护」），在 [69 号候选身份](69-steward-candidate-identity.md) 之后。

## 问题

直递一条线程走 `POST /api/steward/act`。网络失败或超时时，前端只印一句「没做成：…」：原话已经上屏，但服务端**到底执行没执行**没人知道。用户重打一遍就可能把同一件事交办两次 —— 62 号第三轮写的就是这条：「重试先核对上次递送回执，避免网络超时造成重复任务」。

## 改动

1. **一次递话 = 一个 attemptId**（`steward-composer` 之外的 `steward-conversation.handOff` 生成）。`POST /api/steward/act` 新增可选 `attemptId`。
2. **服务端按 attemptId 只执行一次**（`13q` 的 `stewardRunAct`）：内存账本 `attemptId → { at, result }`，最多 256 条、10 分钟过期；同 id 再来直接重放原结果并标 `replayed: true`。只有**真的执行成功**（`ok:true`）才记账 —— 被拒绝的 act 不占 id，用户可以改了再试。进程重启后旧 id 不再算「已执行」，界面本来就只说「未确认」。
3. **只读回执查询** `{ checkAttempt: true, attemptId }` → `{ ok: true, kind: 'attempt_check', applied }`。它**永远不执行** act：没有合法 attemptId 时直接 400，而不是当成一次普通执行。
4. **前端不再谎报失败**：请求抛错（网络／超时）时留一条「递送结果未确认」的提示，原话仍在屏上，并给两枚按钮 ——「核对是否已递到」读回执并如实说「已递到／没递到／现在核对不了」；「重发这一次」带同一个 attemptId，所以就算上一次其实已经落地也只会重放、不会执行第二次。

## 边界

- attemptId 账本只在进程内存：重启后同一次重发可能再执行一次。界面不承诺「重启后仍不重复」，只说未确认；持久化幂等账不在本片范围。
- 未执行成功的 act（`ok:false`）不占用 attemptId；重放只在「真的执行过」时发生。
- 迟到响应：重发期间按钮禁用；`checkAttempt` 与重发都不会 append 第二条用户消息（原话只在第一次上屏）。
- 附件续办、搜索边界、记忆补查 A/B 与第四轮交付修订仍属第三轮其余切片／后续，不在本片。
