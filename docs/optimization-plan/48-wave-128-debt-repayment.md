## §0 为什么叫「偿债」

107 波连续撞到的几件事是同一层地基的裂缝，在它们上面叫 3.0，「更可控」这个承诺对不上：

- **默认值被冻在盘上**：`normalizeConfig` 是 `{ ...defaultConfig(), ...raw }`，而任一次写盘都把**整份合并配置**
  落下去 ⇒ 装过一次的机器上，每个键都实打实写着当年的默认值，此后产品改任何默认值，存量安装一个也吃不到。
  T1 只能靠一次性迁移补三个键；P1 又测出降级再升级会把用户关掉的开关重新打开（Brief §4.2 第 24 条）。
- **陈旧快照盖回新数据**：撤回被垂死回合的旧副本盖回（F7b 修了撤回这一条），但守卫是**按事故一条条手攒的**
  （路由覆盖、权限档覆盖、桌面工具覆盖、任务序号高水位、撤回代数，已第五个），其余读改写调用方跨在撤回上时
  「说 ok 其实没落上」（Brief 第 15–18 条）。
- **测试框架会误杀、会静默挂死**：`taskkill /T` 按父进程号找子孙，进程号复用时带走别人的树（F8 真杀过用户的
  Ollama）；各测试复制的 CDP 客户端在 socket 已关时静默挂到超时（Brief 第 19–20 条）。这两件让「全量绿」
  这句话本身不够可信。
- **G3 三个测试缺口**：简易模式零渲染覆盖、管家壳没有像素基线、人工键盘与真读屏没做。

## §2 128a 设计（主会话定）

**语义**：没碰过的设置跟随产品当前默认；碰过的设置永远照你的。

1. **显式键集合** `configExplicitKeysV1: string[]`，与 `configSchema` 一样是簿记键，随盘落下。
2. **落盘投影**（唯一写口 `writeConfigAtomic` 的输入）：`configSchema`、`configExplicitKeysV1`、**显式键**的值、
   以及**本版不认识的键**（原样保留——更新的版本写下的键，降级时不能被我们抹掉；2.7.0 正是这样保住了 2.8.0 的键）。
   等于默认值且不在显式集合里的键**不落盘**。
3. **什么算显式**：
   - 经 `mutateConfig` 的一次写入里，归一化后**值变了**的键（设置页、API、管家改设置、产品代用户记的状态如
     `lastUsedEngineRoute`，一律同一口径——「被改过」）；
   - 读盘时，盘上**出现**、且归一化后**不等于当前默认**的已知键（手改 `config.json`——手册就教用户这么关开关；
     以及旧版本写下的整份配置）。
4. **迁移按显式键判，不只按 schema 号**：`< 12` 那道三开关迁移跳过显式集合里的键 ⇒ 用户在新版里关掉的，
   降级到 2.7.0（它把 schema 写回 11、但保留不认识的 `configExplicitKeysV1`）再升回来也不会被重开（治第 24 条）。
   `< 9` 的 `engineMode` 迁移同样跳过显式键。
5. **首读即清理**：盘上等于默认、又不在显式集合里的键在第一次读时就被写回投影清掉 —— 不清的话，下次默认
   变了它们会被第 3 条的「手改」规则误认成显式，又冻住。
6. **`changed` 改判据**：是否写盘 ＝ 投影与盘上内容是否不同（不再是归一化过程中的内部标记）⇒ 派生值
   （如没设工作区时 `defaultWorkspace` 取家目录）每次读都重算、但不在投影里，不会造成每读必写。
7. **旧文件**（schema < 13，含降级往返后的）：第 3 条第二款把与当前默认不同的键都记成显式 ——
   等价于今天的行为（不会比现在更差），从此以后才享受「没碰过的跟默认走」。已知代价：降级到旧版期间旧版写下的
   **与新版默认不同的旧默认值**会被当成显式冻住（与今天相同）；在旧版里做的改动**保留**（不丢用户数据优先）。

**粒度**：键级。嵌套对象（`desktopMcp`、`storagePolicy`…）里某个子字段的默认变化，仍要走迁移。

**不改**：`normalizeConfig` 返回的内存视图照旧是整份（所有消费方零改动）；`GET /api/config` 形状不变。

## §2-b 128b 设计（主会话定，2026-09-19；普查由只读代理出表、主会话逐条复核后落刀）

**普查结论**（54 处真调用）：一次被撤回闸丢掉的 `saveSession` **返回值与成功时一模一样**（`02:3143` 返回 `session`），
只有传了 `throwIfStale` 的调用方（今天只有 `updateSessionMetaAttempt` 与撤回自己）知道自己没落上。分类：
- **回合自存**（约 30 处，`runClaudeTurn`／`runOpenAiTurn`／Kimi／`maybeAutoCompact`／steer 排空）：垂死回合的写被丢是**对的**，不动。
- **请求驱动的读改写（会回「成功」却没落上）**：任务开始／更新／核验（`13:1002`、`13:1034`）与任务控制（`02:2325`）——中间还要跑核验命令、
  停子代理，窗口最宽之一；**手动压缩三个引擎**（`10:2204`、`10:1877`、`05b:289`）——中间是数秒的摘要模型调用，回 `ok:true` 带 token 读数；
  技能（`13:153`）、记忆（`13:686/705`）、todo（`13:965`）；管家拜访归档（`13q:452`）。
- **后台读改写**：工作流摘要追加（`08:2080`）、管家回复盖章（`13p:614`）。
- **旁车**：会话笔记（`writeSessionNotes`）、任务变更流水（`bumpMissionChangeSeq` 在被丢的保存之后照样记一笔）、历史快照 —— 都不看撤回代数。
- **驱动器**：任务驱动器在回合之间拿着聊天流那份对象继续跑；撤回只停 `activeChildren` 里的回合 ⇒ 撤回落在两回合之间时，驱动器接着起回合、
  每一存都被静默丢掉（Brief 第 17 条；普查代理提出，**待主会话实证**）。

**设计**：
1. **`mutateSession(id, mutator, { writer, expectGen })`**（02，与 117n-M2 的 `mutateConfig` 同一个形状）：`loadSession` → `mutator(session)`
   （可返回 `{ abort }`）→ `saveSession(session, { throwIfStale: true, writer })`；撞上 `SESSION_STALE_SAVE` 就重新读、重新应用，最多 3 次；
   仍不行抛 `session.rewound_during_write`（调用方回可读的错误，不回成功）。
2. **慢活不重做**：压缩与任务核验这种「先花几秒算、再落盘」的，算之前记下 `rewindGen`，落盘走 `mutateSession(…, { expectGen })` ——
   新读到的代数变了（期间撤回过）就 `abort`，回 `session.rewound_during_write`，**不把基于撤回前历史算出来的摘要写回去**。
3. 上面点名的请求驱动与后台读改写全部改走 `mutateSession`；**变更流水只在保存真落上之后记**。
4. **旁车过闸**：`writeSessionNotes` 与历史快照写之前比一次代数，陈旧就跳过并记一条日志。
5. **驱动器**：每起一个回合之前判「这份对象是不是撤回之前的」（`sessionObjectIsStale`），是就停并记原因。
6. `rewind_superseded` 进 i18n（四份 locale）。
7. **锁**：请求驱动的路由里凡调 `saveSession` 的，要么走 `mutateSession`、要么显式 `throwIfStale`（静态扫描 ＋ owner 数钉住）；
   `mutateSession` 的单测覆盖「撤回插在读与存之间 ⇒ 重做一次后落上」「expectGen 变了 ⇒ 不写、报错」。
**不做**：三个「用户刚切的值在存盘时重新盖一次」的覆盖表（路由／权限档／桌面工具）今天是好的，合并成一张表只是换写法、有风险无收益 —— 不动。

## §3 纪律（每片都适用）

- 进程安全：只杀自己 spawn 的 PID（认子孙须核创建时间）；禁按名字杀；开工与收工各拍一次进程快照对照
  （[46 号文 F8 事故](46-wave-107-release-approval.md)）。用户的正式工作台（`dist/Ruyi-slim`，8765）与 Ollama 是禁区。
- 回归：`run-all --parallel 4`，控制台存档到文件、读 `EXIT=`；**跨轮重现的偶发件按真缺陷取证**。
- 生成器链在最后一次 `src/` 改动后整条重跑；控制字符／CR 扫描；反向验证每把新锁。
- 起服务的演练只用合成数据。
- 本地提交，不推送。

**取证**（scratchpad 探针，只动自己 spawn 的进程）：想直接证明「taskkill /T 会不会带走父号过期、恰好撞号的陌生进程」，没做成 ——

改成每个都等 exit 之后，**3 万次 spawn 也没撞上**。所以 /T 是否核对创建时间**仍未验证**，不赌它。顺带撞见两件真事：
① **libuv 把非 detached 的子进程放进「句柄关闭即杀」的 job** ⇒ 根一死，它们跟着没了；需要按树收的是逃出这个 job 的（detached、非 node 父进程拉起的）；
② **先杀 `conhost.exe` 会把同一控制台上的孙子连带杀掉**，核验脚本自己也没了输出（退出码 1）⇒ 不杀 conhost，它会随最后一个客户端自己走。

**实现**：`dev-harness/lib/kill-own-tree.js` —— 根只杀【还没退出】的自己的子进程（句柄在手，号一定还是它；已退出的不碰）；子孙从一次进程表快照里按父号往下找，
**只认创建时间不早于父进程的**（撞号的陌生人一定比我们的根更老，按构造排除）；动手前按 FILETIME 再核一次启动时间；逐个 `/PID` 不带 `/T`；conhost 不杀、深的先杀。
纯函数 `ownDescendants` 单独导出。codemod：**250 个测试文件 268 处** `taskkill /PID … /T /F` → `killOwnTree(x)`，外加 run-all 的超时收尸与 `kimi-acp-live-probe` 手改；
**27 个自带 CDP 客户端**的 `send()` 在 `socket.send` 前加 readyState 闸（socket 已关时 `WebSocket.send()` 按规范静默丢弃 ⇒ 修前那个 Promise 永不 settle，测试挂到超时、一条 FAIL 都没有）。

**锁**：`unit/kill-own-tree.test.js`（[P1] 合成进程表里撞号的陌生人及其子孙都不算、真子孙含孙辈一个不漏；[P2] 快照解析；[R1] detached 孙子由树遍历收掉；[R1b] 普通孙子随根走；[R2] 根已退出不碰）；
`process-safety.static.e2e.js`（① 全框架零 taskkill /T 调用、run-all 超时走 killOwnTree；② 每个 CDP 客户端都有闸；③ owner 数钉成 251／27）。
**反向**（逐次备份还原、sha256 一致）：塞回一处 `taskkill /T`（数组形与模板串形各一）→ ① 红；拿掉一个 CDP 闸 → ② 红点名文件行号；删掉 lib 的创建时间比较 → 静态锁与 [P1] 同时红。
