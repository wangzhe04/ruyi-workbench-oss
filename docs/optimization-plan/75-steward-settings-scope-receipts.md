# 设置回执与作用域

日期：2026-10-18。基线 `2a5993ef`，实施分支 `codex/steward-3x-implementation`。承接 [62 号方案](62-steward-3x-iterations.md) 第五轮本片，源码尚未发布。

## 用户旅程

管家修改设置后，对话中直接显示实际写入的前后值、对象「如意」、作用范围和生效时机。工具直调、结构化 actions、用户按提议按钮后的结果，均使用执行回包；历史回放与「设置 → 管家 → 行动流水」复用同一个显示模块。实际回执和撤销尝试后由配置域重读，打开设置也重读；保留现有草稿保护，读取失败提示值可能过时，没有增加轮询。模型的 say 或按钮标签不能生成成功回执。

- 应用参数与管家自身参数分别标明范围。未专门枚举的运行参数保守说明为相关功能下次读取配置时使用，不承诺切换在途执行。
- 提问／审批等待：读取新配置后创建的等待使用新时长；已有等待不重新计时，在途回合可能继续持有旧配置。回合无活动超时、管家模型等从后续回合使用。
- 引擎与模型默认：在新建任务时使用，已有任务绑定保持。全局默认权限另标「未单独设置的已有任务也跟随」，不能说只影响新任务。`new_threads` 请求范围也不能夹带全局等待／默认权限设置。
- 仅本任务换模型：打开准确任务，使用顶部已有模型菜单手选。选择从下一回合使用，当前执行继续原模型；管家不通过修改全局 `model` 或服务商来模拟。相对的“强一点”或对象不清楚时需先澄清。
- 「设为新任务默认」仍是模型菜单中的独立操作。普通模型选择显式带 `engineRouteScope: thread`，不更新「上次使用的引擎」；该选择跨后续用户回合保持，因此 `newThreadEngine: last` 也不会间接受到影响。未带作用域的旧调用仍兼容原有记忆上次选择行为。

提醒能力仍有原来的边界：`stewardNotifyPerHour` 是管家主动通知的总频率上限，没有单独的错误豁免。要求“减少普通提醒但保留错误”时，先说明现有能力和核对具体范围，不关闭所有通知，也不能把总上限说成按类型过滤。没有增加新的通知策略或扩大权限。

## 写入与撤销

`steward_config_get` 增加逐键 `settings` 元数据。`steward_config_set` 仍经 free／confirm／forbidden 的既有判据与 `ConfigPatchHooks.applyConfigPatch`；回执的旧值由同一次写锁内的真实快照取得，新值来自写盘归一后的配置。写盘异常不生成成功回执或撤销入口。主端点必须存在；使用服务商时不能把 CLI 的 `model` 默认设置冒充为服务商模型已经改变。

可选 `expected` 必须与 patch 键一致，沿既有规则还原掩码后，在 `mutateConfig` 写锁内比较现值，冲突则整份 `config.conflict`。free 标量且确有变化时提供「撤销这次修改」，通过原 `steward_config_set` 和 `/api/steward/act` 恢复旧值，同时带本次写后值作条件。别的键后来改过仍保留，同键后来改过则不覆盖；并发撤销只有一个能成功。前端强制携带 `undo: true`，服务端拒绝撤销入口中的 confirm／forbidden 设置，导入历史伪造 action 也不能借此绕过确认。

确认类、秘密配置、复合值和无变化的操作不提供一键撤销，界面明确引导到设置核对修改。原有掩码规则继续用于 before、applied、回执和日志。没有新增工具、HTTP 路由、服务器回执库或另一套配置存储；回执与撤销资料内联于既有 `undoRef` 和管家历史章。

丢失撤销回包时显示「未确认」，禁用旧按钮，不自动重发。历史回执表示当时的修改，不能证明今天仍是该值；需要核对时读取当前设置。同键经历其他变化又恢复到完全相同的值时，值比较不区分这段中间历史；这里使用现值 CAS，没有新增全局配置版本账本。
