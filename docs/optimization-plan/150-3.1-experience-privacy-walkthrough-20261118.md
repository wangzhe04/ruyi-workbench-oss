测量噪声：走查期间多 agent 并发，CPU 负载最高 93%，绝对毫秒偏大 2–5 倍；结论以计数、同进程开/关配对和占比为准。主会话在负载 40% 时复跑 `memory-semantic.e2e.js`、`memory-explicit-semantic.e2e.js` 各 2 次均 ALL PASS；负载 93% 时两件各 2 次 FAIL，且都落在「期望重排 / 期望语义命中」的断言上——这不是噪声，而是 §2 的同一机制：负载下语义预算被回验 I/O 吃光，产品退化为纯关键词。

## 1. 总判断：四个共同根因

1. **同一事实在循环里被反复回验。** 这是语义慢、记忆注入慢、加密慢的共同主因，而不是模型推理本身：
   - 记忆预检每回合至少 4 次全量读注册表（语义开/关都付），加密时每次把全部记忆解密一遍；
   - 会话全文检索的 `cap.assert` 遍历全部来源，被乘进逐行、逐 shard、逐 96 字窗的循环（160 会话每请求 1.7–2.1 万次）；
   - 语义每 4 片一批要跑约 5 次 beforeEncode 全量回验，真实模型无守卫时 46–52 片/秒，进管线后每请求只编 10–26 片；
   - 加密维护每次 status 轮询都整包读取并哈希备份包，每次 flush/普查重起 PowerShell 现场编译 C#。
2. **失败即锁死，而不是降级。** 语义 worker 起一次失败此后整轮报错；预检判 stale 就把核心记忆一起清空；加密冷进程失败后 `hold()` 永不退出，下次启动拒绝，只有隐藏 CLI 能解；移走备份包面板永久 503。
3. **功能做了，但没到用户眼前。** 每轮记忆摘要写进一个永久隐藏的节点；搜索命中的较早线程不画；`work_data_*` 错误码在 locale 里一条文案都没有；前端从不读 `processRestartRequired`。现有 e2e 读的是隐藏节点的 textContent，所以测试是绿的。
4. **隐私检测有真实泄露缺口。** 标题/摘要先截断再识别、URL 密码含 `@` 只保护到第一个 `@`、短学习值（`on`/`s`/`a`）污染整个会话并能让请求整轮失败。

另一个结构性观察：3.1 的验收几乎全部投在原生证明（句柄复用、访问时间漂移、Job 收尾、冻结绑定）上，SR 门里没有「发消息到出字」「搜索结果是否画出来」「失败后用户能否自救」这类体验门。§7 建议补上。

## 2. 语义检索与记忆注入（A、B 线）

用户怀疑的「等语义做完才发」：**语义重排本身最多等约 250 ms 就回退关键词**（06hb `prepare` 默认预算 250、06hc `deadlineMs:250`），开机预热在 `setImmediate` 里不阻塞。真正拖慢发送的是预检的反复回验和两项与记忆无关的串行等待。

### 2.1 发消息 → 请求到达 provider（provider 引擎，全部串行 await；B 线实测）

| 条件 | 合计 | 主要构成 |

## 7. 优化方案：分批与通过标准

### 批 3 · 结构与体验

- 后台增量建索引与编码（S6、S14）：空闲时分片执行、让出事件循环、可被维护钩子暂停；向量按模型指纹 + 片段哈希 + 来源 identity 落盘，加密模式同样加密；删除会话只清该会话向量；大文本构建可续做、超预算会话跳过并标记（S7）。通过标准：首次搜索只付词法成本；重启后不必重新暖机；400 会话后台建完 ≤60 s。
