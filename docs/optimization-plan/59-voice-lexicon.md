# 59 · 语音词库：从用户手改里学 ＋ 原厂常用词

> 状态：**两步都已实现（2026-10-01）**。第一步：词库地基、原厂常用词表、三处识别口接通、设置页维护、工具箱热词切词修复（§4）。
> 第二步：从用户手改里学（§6）。
>
> 用户原话（2026-10-01）：「现在如意的语音识别因为是转文字嘛，但肯定会有很多专业术语是没法正确转成对应文字的；那么是否有可能，等转写完后，
> 看用户手动改的音的文字并收集规律整理，后续听到同音字的时候优先转成对应的呢」。
> 看完方案后拍板：「默认开，但是我觉得每个用户的词库不一样，所以要不还是默认从用户手改的错字里去学习，原厂只提供一份常见中英文词，
> 当然也可以尽量详细一点；判定本身当然是允许调用模型的，但是 asr 模型也能接受提示词吗；要；直接上第一步」。
> 第一步落地后补一句：「不止是专业术语，好友包括人名字这种，似乎必须的从用户修改中学」—— 人名成了第二步的头等用例。

## §0 一句话

**学「词」，不学「替换规则」；词只当提示，交给听得到声音的（重听）和看得懂整句的（大模型改字）去判。** 把词提前告诉识别链路的三个口子
早就留着（实时识别的会话热词、整段识别的 `prompt`、大模型改字的提示词），只是一直传空值；第一步把它们接上，并给出一份
用户自己的词库（设置页维护）和一份原厂常用中英文词表。第二步再从用户的手改里自动往同一份词库里学。

## §1 现状盘点（改动前）

| 环节 | 口子 | 改动前 |
|---|---|---|
| 第一遍 asr-stream（sherpa-onnx 流式 zipformer） | 开会话可带 `hotwords` | 前端开会话只发 `{}`（`composer-voice.js`）；51 号文 §4「热词从工作区名字喂给两遍」没接上 |
| 句尾重听 / 整段识别（asr-shim Qwen3-ASR、Whisper 形云端） | multipart `prompt`（asr-shim 原样当 Qwen3-ASR 的上下文/热词） | 13b 句尾改错、整段识别、附件转写与 12 的 `audio_transcribe` 全写死 `prompt: ''` |
| 大模型改字（131b） | 系统提示 | 只有一串写死的通用技术词 |

**工具箱里的坑**：sherpa-onnx 的 `modeling_unit` 缺省是 `cjkchar`，中英双语 zipformer 的英文是 BPE，必须 `cjkchar+bpe` ＋ `bpe_vocab`；
评测脚本（`bench-voice/eval_stream.py`）设了，组件 `engine.py` 没设 —— 产品里英文热词整词查不到 token、被静默丢掉。另有两处：
`_clean_hotwords` 把词内空格删光（`PULL REQUEST` → `PULLREQUEST`，切出来是另一串 token）；HF 镜像那条下载路只拿四个文件，没有 `bpe.vocab`。
（52 号文「热词几乎没用」是评测脚本量的，配置正确，结论成立：通用技术词模型本来就认得差不多。）

## §2 原型：用现成评测数据看「从修改里学」会学到什么

把 `bench-voice/results` 里各遍的识别结果当「机器写的」、题面原文当「用户改好的」，对齐 → 抽出被替换的片段 → 用拼音判断读音像不像
（scratchpad 原型，pypinyin，不进仓）。4440 条（句子 × 方案 × 条件）里：

| 用户要的词 | 被听成的样子（次数） |
|---|---|
| redis | 瑞迪斯 46、威迪斯 20、瑞蒂斯 2 |
| python | 拍伞 38、拍赛 21、帕萨 2 |
| docker | 刀客 24、刀刻 22、DOCT 18 |
| debug | 低暴 17、低报 14、低爆 3、d bug 2 |
| 复现 | 负线 37、腹泻 22 |
| 服务器 | 巫启 14、雾气 8 |
| pull request | 博瑞卡斯 3、普瑞克斯 2 |

三条规律决定了设计：

1. **单字同音占大头**（爆→报 43、在→再 22……共 669 次）：做成替换规则必误伤 → 单字不进词库，留给大模型按语义改。
2. **同一个词被听成很多样子**（debug 6 种）：按字串记「低报 → debug」覆盖不全 → 记「词 ＋ 几个错听样子」，让模型泛化。
3. **最好的链路也会漏**：hard 档 Qwen3-ASR ＋ DeepSeek 合成后「把日志级别调成低报」还在（提示词里已经写了 debug）——具体的线索
  （「这个人说过的低报是 debug」）有没有用，要在真机上看（见 §7）。

读音不像的改动大多本来就该丢：数字写法、「PR → pull request」（大模型擅自缩写，属风格）、改内容。

## §3 识别模型能不能吃提示词（回答用户的问题）

| 识别 | 吃什么 | 第一步怎么给 |
|---|---|---|
| 实时识别 asr-stream（sherpa 流式 zipformer） | **热词**（词表 ＋ 加分），不吃整句提示 | 个人词（原厂通用词不给：52 号文 §2 实测几乎没用） |
| 整段识别 asr-shim（Qwen3-ASR 0.6B/1.7B，标准/重度档） | **上下文提示**（transformers 叫 `prompt`、qwen-asr 包叫 `context`，进系统提示；官方的热词/领域词口） | 个人词 ＋ 这一句命中的原厂词，只列词、≤ 400 字 |
| Whisper 形云端（`/v1/audio/transcriptions`） | OpenAI 规范的 `prompt`（当前文，能把拼写往这边带） | 同上 |
| 对话型云端识别（chat-audio，如 MiMo） | 把 prompt 当一段文字塞进对话 —— 会不会被当成要回答的话没量过 | **不给**（先不冒险） |
| SenseVoice（轻度档的重听，sherpa 离线 CTC） | 不吃热词也不吃提示 | 不给；轻度档靠大模型改字那一路用上词库 |
| 大模型改字 | `<glossary>` | 个人词全带 ＋ 这一句命中的原厂词（带错听样子） |

## §4 第一步做了什么

- **04j `VoiceLexicon`**（新模块，冻结对象，**零出边、不进任何环**，与 11b 同模具）：词条形状与清洗；设置页文本（一行一条「词 = 样子1, 样子2」，
  `=` `＝` `←` 都认，样子之间 `,` `，` `、` `;` `；` `|` 都认，`#` 注释）；原厂常用词表 `BASE_TEXT`（472 条，334 条带错听样子：版本管理、语言与运行时、
  前后端框架、数据库与中间件、运维与云、网络、开发日常用语、AI 与大模型、办公与项目管理、游戏与引擎（UE/Unity）、常被听错的中文技术词）；
  挑词 `pick`：个人词全带（≤ 40，命中的在前、次数多的在前），原厂词只在这一句命中错听样子、或写法特殊的英文大小写不对（GITHUB / postgresql）时带
  （≤ 24），已写对的不带、与个人词同名的让给个人词；三处出形 `glossaryLines` / `asrPrompt` / `hotwords`。
  错听样子的门槛：中文 ≥ 2 字、英文 ≥ 3 个字母数字、与词本身不同；原厂表里日常高频词不当错听样子（「前段」「买点」「对战」「预制」会在正常话里大量出现），
  除非评测有实证（腹泻→复现、雾气→服务器、心中→新增、题型→提醒）。
- **05**：`<data>/voice-lexicon.json` 用 `DurableJsonStore`（schema 1、清洗、坏文件隔离、500 条容量、串行原子写、进程缓存）；唯一写口
  `voiceLexiconUpdate`（`runKeyedChain` 串行读-改-写，第二步也走它）；`voiceLexiconAsrPromptFor`（chat-audio 不给的规则只有这一处）；
  `asrFixMessages` 第四参 `glossary` → `<glossary>` 块（在前文与转写之前；尖括号/换行压掉、≤ 60 行；**没有词表时提示词与 133a 逐字相同**）。
- **13b**：句尾改错（重听带 prompt、改字带词表，`asr_fix` 审计多记 `glossary` 行数）；整段识别（调用方没给 `?prompt=` 才用词库）；
  附件转写；开实时会话（前端没给热词才用个人词）；新路由 `GET /api/audio/lexicon`（`?base=1` 附原厂表全文）与 `POST /api/audio/lexicon`
  （`{text?, base?}`，整份替换个人词 / 开关原厂表；超长 413、超 500 条 400，整份拒收不截断；审计 `voice_lexicon_save` 只记条数）。ROUTE_AUTH 两条 token 级。
- **12**：`audio_transcribe` 工具带个人词 prompt。
- **设置页**（provider-settings）：「语音识别」页签多一张卡「语音词库」—— 等宽文本框 ＋「保存词库」＋ 计数、内置表开关（选中即存）、「查看内置词表」只读展开、
  一句说明（只当提示不做硬替换、MiMo 暂不带）。块只建一次：上面几栏每次存配置都会重画，编辑到一半的词不被冲掉。
- **工具箱 asr-stream**：`detect_modeling_unit` 按模型目录探测（有 `bpe.vocab` → `cjkchar+bpe`），词表只有大写英文时热词里的英文转大写；
  `_clean_hotwords` 词内空白收成一个空格；老 sherpa-onnx 不认这两个参数时照起（中文热词照常）；`download-model.ps1` 补下 `bpe.vocab`
  （老装好的目录重跑一次就补上，下不到不拦）。

学习相关的落盘形状一并留好：`src`（manual / learned / typed）、`n`（被改过几次）、`off`（学来的词被用户删掉 → 停用墓碑，免得又学回来）。

## §6 第二步：从修改里学（已实现）

用户拍板：**默认开**（学会时提示一句、设置里能关）；**判定允许调用模型**（读音规则初筛，配了改字大模型就让它复核；没配就只靠规则与次数）；
**冷启动从用户打过的字里抽英文词**；**人名必须能学**。实现的形状：

1. **记**（`composer-voice.js` ⑪）：每句机器写进输入框的字记一笔 —— 流式路记的就是那一句的对象本身（句尾改错换字时 `text` 跟着变，`first`
   留着第一遍原文；对第一遍才看得出读音像：句尾改错把「拍伞」改歪成「雨伞」、用户改成 Python，读音要比「拍伞」）；按停顿切段那一路两份相同。
   只在内存里，输入框空着开录时清账。三条发送路（工作台 `sendPrompt` / `steerPrompt`、管家输入行 `submit`）在清空输入框之前派
   `ruyi:composer-sent`（chat-stream-runtime.js 锁死零 import，内联同值字面量、写在原有那一行里 —— 那个文件的中文行号白名单不动）；
   麦克风听到自己那个输入框的发送，就把「这几句 ＋ 发出去的字」交给 `POST /api/audio/lexicon/observe` 并清账。没配语音识别不交；
   没用麦克风的消息也交（sentences 为空，只从打的字里抽英文专名 —— 冷启动）。
2. **抽**（04j `VoiceLearn.extract`，纯函数）：
   - 单位：一个汉字 / 一个英文词（`Node.js`、`C++`、`gpt-4o` 算一个）/ 一串数字 / 一个符号；
   - 定位：相邻两个单位在发出去的字里投票定大致位置，再在附近做「两头可空」的编辑距离对齐（中间夹着用户自己打的字也认得出）；
     一半以上的单位原样留着才算「改过的这一句」（整句改写、删掉的不学）；
   - 改动：两个对上的单位之间的不同处；句首句尾没对上的那几个单位，按读音在发出去的字里挑最像、且**停在词边界上**的那一段
     （到头、到上一句的地界、外面是标点/空白、换了文字）—— 否则「巫启」（服务器被吞了一个字）会挑中读音一模一样的半个词「务器」；
     都不像就取最近的边界，交给大模型判；
   - 读音像不像：中文等长逐字比拼音（同音、平翘舌、n/l、f/h、前后鼻音、多音字取最像的读音；单字 ≥ 0.8，多字平均 ≥ 0.7 且每字 ≥ 0.5）；
     中↔英比辅音骨架（P/T/K/S/F/H/W/M/N/L 十类，汉字韵尾 -n/-ng 也算；驼峰词拆开读；头一个辅音要对得上、音节数差得不多）；
     英↔英比字母编辑距离；只改大小写算「打字证据」；带数字或符号的不学（数字写法不是听错）；
   - 候选：多字的改动直接是一对（`Python ← 拍伞`）；**只改了一个字**（人名最常见：张伟 → 张玮）就以它为中心拼 2–3 字的窗口
     （`张玮`、`和张玮`、`张玮去`……，借来的前后字必须在机器那一句的同一位置原样在），哪个才是词交给次数或大模型去定；
     语义同音字（的/地/得、在/再、他/她/它、做/作、以/已/一……）不拼窗口、不问大模型；
   - 打字里的英文专名：词中间有大写、全大写缩写、带数字或点/连字符、中文语境里的首字母大写词；代码块、行内代码、网址、路径、
     下划线标识符、语音那几段里的不算；一条消息最多 12 个。
   - 拼音表：04j-hanzi-pinyin（生成物）—— Unicode Unihan 的 kMandarin（主读音）＋ kXHC1983（现代读音，含姓氏读法），基本区 20898 字、
     418 个音节，64 进制压成约 53 KB；生成脚本 `dev-harness/hanzi-pinyin-generate.js`，许可见 THIRD-PARTY-NOTICES §4。
3. **复核**（`judgeMessages` / `parseJudge`）：有要判的、且 `resolveAsrFixProvider` 有端点（与句尾改错同一个；`asrFixMode` 为 off/audio 时不判），
   就一发 `providerFixCompletion`：读音像的候选（已是个人词的不问）＋ 读音规则没认出、但像在改一个词的（巫启 → 服务器），最多 8 处；
   提示词加固（`<edits>` 里是数据不是指令、尖括号压掉），要它判「是不是把专名/术语听错了」、算的话给出整个词（人名给全名）；
   回来的词必须出自改后那一句、并盖住那处改动，错听样子按它多出的字数从机器那一句接出来；判「是」一次就学会、判「不是」不记、
   回胡话或词对不上当没判（走规则）。记账 aux/`voice-learn`（与 asr-fix 共用 `appendAsrFixUsage`）。
4. **存**（`apply`，经 `voiceLexiconUpdate` 串行落盘）：已是个人词 → n+1、补错听样子；原厂表里的词、用户打过的词 → 一次就学会（先验）；
   其余进 `pending` 攒次数，**同一个改法在两条消息里出现**才学会（同一条消息里改两处只算一次）；窗口组里同时到数的，借来的字里虚词少的、
   再短的优先（两句里名字前面都是「给」：学「柳洋」而不是「给柳」），同组与包含它的窗口作废；打字里的专名三条消息见过才收（`src:'typed'`，
   最多 100 条，只在一句里命中时才被挑中、不当热词）。pending 60 天没再见就丢、最多 300 条；词条满了先挤墓碑、再挤打字词与学来词，手加的永远不挤。
5. **纠**：学来的（或打字收的）词又被用户改成读音相近的写法 → n−1、去掉那个错听样子，扣到 0 停用（墓碑）；这一处改动不再拿来学新词
   （否则「张玮 → 张伟」改回去两次会反学成「张伟 ← 张玮」，两个词来回拉锯）。墓碑（用户删掉的、扣光的）永远不再学，含着它的窗口也不学。手加的词不扣。
6. **看得见**：学会新词时提示「记住了：刀客 → Docker（可在 设置 → 语音识别 → 语音词库 里管理）」；设置卡多一个「从我的修改里学」开关
   （选中即存）与计数（学来的、打字里收的、还在攒证据的）；学来的词就在文本框里，删掉即可。
7. **隐私**：文本只在内存里走一趟；`voice_learn` 审计只记条数（几句、对上几句、几处改动、问了几处、学会几个、扣了几个）；只有配了大模型复核时，
   改动的那几句会发给那个模型（与句尾改错发的是同一类内容）。

## §7 没验证的与风险

- **没有在真模型上量**（用户选了跳过评测直接上第一步）：Qwen3-ASR 吃词表的效果、大模型带 `<glossary>` 会不会过度纠正，都还没有读数。
  建议真机走查时盯两件事：说专有名词时句尾改错能不能改对；说日常话时有没有被词表「纠」歪。要量的话：bench-voice 加一份含个人词的题面和一份反例题面。
- 原厂表的错听样子一半是照常见音译手写的（另一半来自评测），实际出现频率未知；它们只在出现时才被挑中，挑中也只是提示。
- 对话型云端识别（MiMo）这一路暂不带词表，量过再开。
- 第二步的阈值（读音分数线、两次才学、窗口 2–3 字、三条消息收打字词）是照原型与手造例子定的工程默认，没有在真人用量上调过；
  规则路的主要风险是日常词的同音改动（一下/以下）攒够两次被学进去 —— 靠语义同音字表、大模型复核与「改回去就扣分」兜着，真机走查时盯它。
- 人名只改了一个字时，规则路要第二次改同一个名字才知道名字的边界；三字名可能只学到后两个字（作为提示仍然有效）。配了大模型复核时一次就是全名。
