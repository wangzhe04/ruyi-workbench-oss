# Traveler 4.0 概念稿：可迁移的任务旅程

状态：**概念稿 v0.1（2026-08-05，基于 `v2.4.1` / HEAD `4f99608`）**。本文用于探索 Pretender 之后的下一个大版本方向，**不是 Traveler 的范围拍板、版本承诺、波次计划或发布时间表**。Pretender 3.0 的 Product Ready / Release Ready 条件仍以 [`PRETENDER-PLAN.md`](./PRETENDER-PLAN.md) 与 [`PRETENDER-METRICS.md`](./PRETENDER-METRICS.md) 为准；Traveler 的工程实施不得抢跑或稀释 Pretender 的收口。

候选产品名：**Ruyi Traveler 4.0**
候选副题：**可迁移的任务旅程（Portable Missions）**

---

## 0. 范式主张

**Pretender 让 Mission 成为权威对象；Traveler 让 Mission 能够跨时间、工作圈、设备、执行环境和接手者继续前进。**

Traveler 的核心不是“把聊天记录同步到另一台电脑”，也不是“做一个新的 Slack”。它要解决的是一张任务单在离开当前进程和当前机器后，如何仍然携带并诚实呈现：

- 已经完成什么、当前停在哪里、下一步是什么；
- 哪些事实、成果、决策和外部副作用已经发生；
- 哪些文件与能力可以带走，哪些凭据和权限必须重新绑定；
- 可以从哪里安全继续，哪些步骤需要重做或人工判断；
- 谁拥有查看权、决策权和执行权；
- 任务完成后如何把成果、证据和未完成项可靠送回。

一句话北极星：

> **任务无论走到哪里，事实、边界、证据和控制权都还在。**

## 1. Traveler 与协作软件的区别

多人协作是 Task Capsule 自然解锁的结果之一，但 Traveler 不应以频道、即时消息和在线状态为中心。

| 频道式协作 | Traveler 的 Mission-first 协作 |
|---|---|
| 先聊天，再从消息中提炼行动项 | 先建立 Mission，讨论与决定挂在任务之下 |
| 状态依赖人工汇报 | 状态来自权威 journal、checkpoint 与执行回执 |
| 文件是消息附件 | 文件是输入、成果、证据或可恢复点 |
| 交接依赖复制上下文 | Capsule 携带最小必要上下文、能力要求与恢复契约 |
| “完成”常是一条消息 | 完成包含验收、成果、未完成项、成本、审计与可恢复度 |
| 权限多由工作区成员身份隐含继承 | 查看、决策、执行与再转交权显式分离、重新确认 |

因此 Traveler 更接近“任务协作系统 + Agent 执行运行时 + 本地可信账本”。即时讨论可以存在，但只能是 Mission 的通道，不能重新成为产品的信息架构中心。

## 2. 北极星旅程

### 2.1 带到自己的另一台设备

用户在办公电脑上暂停一张 Mission，导出 Capsule，在出差电脑上导入。Traveler 对照目标环境能力，重新映射工作目录、提示重新授权，从最后一个安全 Waypoint 继续；原电脑保留只读旅程记录或在执行租约归还后继续。

### 2.2 正式移交给同事

发送者选择接收者、交接范围、执行权、决策权和有效期。接收者先在“交接箱”检查来源、完整性、敏感信息、文件变化、环境差异和不可逆事项，接受后才取得执行权。发送者端进入“已移交 / 只读”，避免两边同时执行高风险动作。

### 2.3 创建独立副本

接收者基于原 Mission 创建新分支，继承必要上下文和成果，但取得新的 Mission 身份。两边可以走不同路线，后续只显式比较成果与决策，不自动合并外部副作用。

### 2.4 发给客户或审核者验收

接收者不需要取得工具执行权，只能查看被授权的成果、证据和问题，完成批注、回答、批准或签收。内部原始对话、密钥、工具配置和未授权文件不随包暴露。

### 2.5 交给更合适的执行环境

OCR 去具备 Windows OCR 的机器，构建去高性能工作站，敏感数据留在内网节点，外出设备只负责监督和决策。环境切换仍遵循同一 Capsule、Waypoint、Execution Lease 与 Evidence Bundle 语义，不另造一套远程任务状态机。

### 2.6 带着结果回来

接收方完成任务或阶段性交付后生成“回程 Capsule”，只携带新增旅程段、成果、证据、决策、外部副作用和未完成项。来源端导入后把它挂回原 Mission 的旅程台账，不复制整张任务，也不静默覆盖来源端变化。

## 3. Task Capsule：Traveler 的核心原语

### 3.1 Capsule 是什么

Task Capsule 是一个可验证、可加密、可审阅的任务交接包。它不是运行中进程的休眠镜像，而是由最后一个持久化一致点生成的**恢复合同**：目标端知道有什么、缺什么、能从哪里继续，以及继续后可能发生什么。

候选扩展名：`.ruyi-task`。物理格式可采用带签名清单的归档容器，但格式决策必须在威胁模型、流式大文件和版本兼容评审后冻结。

### 3.2 Capsule 建议内容

```text
capsule/
├─ manifest.json                 # schema、来源、摘要、内容哈希、兼容范围
├─ mission/
│  ├─ snapshot.json             # 导出时权威 Mission 投影
│  ├─ changes.ndjson            # 有界 change records / journal
│  └─ resume-plan.json          # 安全驻点、未完成步骤、恢复等级
├─ handoff/
│  ├─ offer.json                # 发送者、接收者、模式、范围、有效期
│  └─ authority.json            # 查看/决策/执行/再转交权限
├─ capabilities/
│  ├─ required.json             # 所需 OS、工具、模型与版本范围
│  └─ source-environment.json   # 来源环境事实，不含凭据
├─ artifacts/
│  ├─ index.json                # 路径、角色、大小、哈希、嵌入策略
│  └─ blobs/                    # 选择内嵌的内容寻址文件
├─ checkpoints/                 # 可携带的文件恢复点和引用
├─ evidence/                    # 成果、外部副作用回执、验收证据
├─ report.html                  # 无 Traveler 时可读的脱敏只读报告
└─ signatures/                  # 清单签名与接收者加密材料
```

逻辑上至少包含：

1. **身份与目标**：Mission 身份、标题、委托书、验收标准、来源关系；
2. **进度与状态**：已完成里程碑、当前步骤、剩余步骤、未决 Intervention；
3. **恢复证据**：checkpoint、changeSeq、Run/turn 终态与恢复等级；
4. **成果与输入**：嵌入文件、外部引用、内容哈希、路径映射建议；
5. **环境合同**：需要的工具、模型、OS、存储、网络和可选降级；
6. **权限合同**：接收者可以查看、回答、执行、再转交或仅审阅哪些内容；
7. **副作用台账**：已经发出的邮件、写入的远端系统、不可逆命令和幂等回执；
8. **兼容与完整性**：schema 版本、最低 Traveler 版本、签名、各内容块哈希。

### 3.3 默认不得携带的内容

- API Key、OAuth token、Cookie、浏览器登录态、SSH Key、系统凭据；
- 来源机的明文环境变量、凭据文件或无关用户目录；
- 未经用户选择的大型工作区、缓存、依赖目录或构建产物；
- 无法解释来源和用途的临时文件；
- 活跃进程、内存、socket、未终态化的模型流或工具子进程；
- 接收者无权查看的原始对话、个人记忆或其他 Mission 数据。

目标端只能获得能力要求和凭据槽位，必须使用自己的凭据重新绑定。

## 4. Capsule 生命周期与传输模式

### 4.1 生命周期

```text
draft
  → preparing       # 暂停新动作、收敛到持久一致点、扫描敏感信息
  → ready           # 生成内容清单、恢复计划与预览
  → offered         # 发出但尚未被接收
  → accepted        # 接收者确认交接范围
  → imported        # 完成能力检查、路径映射与凭据重绑
  → resumed         # 目标端取得执行租约并开始新 Journey Leg
  → returned|closed # 返回成果或在目标端收工

offered → rejected|expired|revoked
preparing|imported → blocked       # 不完整、篡改、能力不足或版本不兼容
```

Capsule 文件被复制不代表执行权已经转移。`accepted`、`imported` 与 `resumed` 必须是不同状态，执行租约只有在接收、环境检查和用户确认全部成功后才发生变化。

### 4.2 正式移交（Transfer）

- 保留同一 Mission 的来源关系与旅程连续性；
- 接收者取得新的 Journey Leg 和活跃执行租约；
- 来源端默认只读，可撤回尚未接受或已过期的交接；
- 接收后如需夺回执行权，必须通过明确的接管/归还流程；
- 高风险动作禁止两个环境并发执行。

### 4.3 创建副本（Fork）

- 接收端创建新 Mission 身份并记录 `parentMissionId` / `originTransferId`；
- 来源端和接收端互不冻结，可独立执行；
- 后续只允许显式比较、挑选成果或发起新的合并任务；
- 权限决策、外部副作用和不可逆动作不得自动合并。

### 4.4 只读审阅（Review）

- 不授予工具调用和 Mission 控制权；
- 可按范围查看成果、证据、成本、未完成项和指定原文；
- 可提交批注、答案、批准或验收结果；
- 返回内容作为 Evidence / Decision，而不是目标端 Run。

## 5. 导入体验与安全续办

### 5.1 “交接箱”先于任务坞

Capsule 导入后先进入隔离的交接箱，不直接写入工作区、不自动解压可执行内容、不启动脚本或工具。接收者必须先看到：

- 发送者身份、签名状态、交接模式和有效期；
- Mission 目标、当前进度、安全续办点和未完成项；
- 将写入或映射的文件、总体积、内容类型和敏感性；
- 所需能力与本机差异；
- 需要重新绑定的凭据与权限；
- 已发生的不可逆事项和目标端不得重复的动作；
- 导入后将获得的查看、决策、执行和再转交权。

接收者可以选择接受并继续、仅查看、另起副本、拒绝或保存待处理。

### 5.2 接收端出现什么

接受并完成导入后，Traveler 在接收端建立：

- 一张带“来自谁 / 从哪里接手”标记的 Mission 卡；
- “你接手前发生了什么”的确定性摘要与完整来源展开；
- 已携带的成果、输入、checkpoint 和外部副作用账；
- 路径映射、能力缺口和凭据重绑状态；
- 新的 Journey Leg，以及其设备、工作圈、执行引擎和租约事实；
- “从安全驻点继续 / 仅审阅 / 创建副本 / 拒绝交接”控制面。

没有安装 Traveler 或版本无法执行时，只允许打开脱敏只读报告和普通成果；不得通过报告中的链接或脚本自动取得执行能力。

### 5.3 四级恢复合同

| 恢复等级 | 含义 | 目标端行为 |
|---|---|---|
| **exact** | 存在完整、可验证 checkpoint，当前步骤已终态化 | 从下一步或精确 checkpoint 继续，不重复已完成工作 |
| **step** | 当前步骤未完成，但步骤边界与前置成果可信 | 从当前步骤开头重做，保留此前成果 |
| **manual** | 上下文可读，但无法证明自动续办安全 | 阻止自动执行，由接收者选择重试、换路或终止 |
| **read-only** | 已完成、能力不兼容或未授予执行权 | 只查看、验收或基于它创建新 Mission |

恢复等级必须由 checkpoint、journal、执行回执和能力检查计算，禁止由模型文案猜测。

### 5.4 不同导出阶段的续办语义

| 来源端状态 | Capsule / 接收端语义 |
|---|---|
| 尚未开工 | 回到交办确认卡，接收者确认后建立新 Run |
| 一个步骤刚完成 | 从下一步骤继续 |
| 正在执行某一步 | 收敛或中止活跃执行，从最近安全 checkpoint 继续；半截输出不冒充成果 |
| 正在等待决定 | 仅在对应决策权被交接时进入接收者“需要你”，否则仍归原决策者 |
| 因能力不足阻塞 | 保持 blocked，目标端重新计算是否已具备能力 |
| 存在崩溃中间态 | 标记 indeterminate，不自动重放高风险动作 |
| 已收工 | 导入为成果与证据，可验收或 Fork，不自动重开原 Mission |

## 6. 领域模型候选

Traveler 应扩展 Pretender 的领域地基，而不是建立平行任务系统。

| 对象 | 作用 | 关键约束 |
|---|---|---|
| **Mission** | 跨环境保持稳定的任务身份 | 继续作为一级权威对象；不得被 Capsule 文件名替代 |
| **Journey View** | 一张 Mission 跨多个执行环境的旅程投影 | 是投影，不是第二套状态机 |
| **Journey Leg** | 在一个设备/工作圈/执行租约下的执行段 | 引用 Session、Run、引擎、环境和起止 Waypoint |
| **Waypoint** | 可导出、移交或恢复的持久一致点 | 包含 changeSeq、checkpoint、外部副作用边界与恢复等级 |
| **Transfer** | 一次发送、接受、拒绝、撤回或过期记录 | 稳定 transferId；传输状态与执行状态分离 |
| **Execution Lease** | 当前谁/哪个环境可以执行高风险动作 | 带版本、持有者、过期和接管协议；不承诺离线环境的虚假 exactly-once |
| **Capability Manifest** | 来源需求与目标能力的可比较合同 | 不含凭据，只描述能力、版本和重新绑定槽位 |
| **Evidence Bundle** | 一段旅程产生的成果、回执与验收证据 | 内容寻址、可追溯、区分可恢复与不可逆 |

Pretender 已将 Mission 1:N Session 正式移到 3.1。Traveler 的跨设备/跨接手者语义天然依赖一张 Mission 关联多个 Session、Run 和环境，因此在 Traveler 数据契约冻结前必须先完成或重新拍板这一前置关系，不能继续把 `missionId=sessionId` 的 1:1 派生当作长期跨设备模型。

## 7. 安全、隐私与信任边界

### 7.1 完整性与来源

- Capsule manifest 和每个内容块使用内容哈希；任何缺失或篡改均阻止执行态导入；
- 支持发送者签名、接收者加密和显式未签名警告；
- 签名证明“由谁打包、内容是否变化”，不自动证明发送者可信；
- schema 迁移必须产生新版本清单和迁移审计，不可静默改包。

### 7.2 隔离导入

- 防 path traversal、绝对路径覆盖、符号链接逃逸、归档炸弹和超大文件资源耗尽；
- 可执行文件、脚本、Office 宏和未知二进制默认隔离，不因导入而运行；
- 文件落盘前展示规范化目标路径和冲突策略；
- 导入失败不修改既有 Mission、工作区或权限状态。

### 7.3 最小披露

- 导出前提供完整 / 脱敏 / 仅成果 / 自定义范围预览；
- 个人记忆、其他 Mission、隐藏系统提示和无关工作区文件默认不携带；
- 每个文件和原文片段记录包含理由与接收者范围；
- 接收者对 Capsule 的再转交权必须单独授权。

### 7.4 权限重新绑定

- 来源端权限不在目标端隐式继承；
- 决策权、工具执行权、文件写入权和再转交权分别表达；
- API Key / OAuth / 浏览器会话由目标端自己的安全存储重新绑定；
- 接收者拒绝某项权限时，系统重新计算可执行范围并诚实降级。

### 7.5 外部副作用与重复执行

- 已发送邮件、付款、远端写入等只携带回执和幂等信息，不携带“可全局撤销”的虚假承诺；
- 目标端继续前必须核对未终态工具调用，无法证明时进入 manual / indeterminate；
- Capsule 重复导入按 capsuleId / transferId 幂等，不重复创建执行租约或实际动作；
- 离线移交无法证明全局唯一执行时，宁可要求人工接管，也不宣称 exactly-once。

## 8. Local-first 传输策略

Traveler 的第一版不应强制云账号或中心服务器。

建议按能力递进：

1. **文件 / U 盘 / 局域网共享目录**：最容易验证 Capsule 自洽性、离线能力和安全边界；
2. **用户自选同步介质**：网盘、Git 附件、NAS 等只负责搬运加密 Capsule，不成为权威状态源；
3. **可选 Relay**：提供发送、撤回、过期、收件和回程传递，但不代替本地 Mission journal；
4. **实时协作**：在身份、Execution Lease、冲突和离线重连契约成熟后再评估。

即使将来有 Relay，用户也应能导出标准 Capsule 并离开服务；平台不得以云端锁定换取协作便利。

## 9. Traveler 4.0 候选核心范围

### 9.1 推荐纳入 4.0

1. `.ruyi-task` Capsule 的生成、预览、签名、加密、导入与幂等；
2. 同一用户跨工作区/跨设备的离线续办；
3. 正式移交、创建副本、只读审阅三种模式；
4. 单一活跃 Execution Lease 与明确接管/归还；
5. exact / step / manual / read-only 四级恢复合同；
6. 能力对账、路径映射、凭据重绑和诚实降级；
7. 回程 Capsule 与 Evidence Bundle；
8. 无 Traveler 时的脱敏只读报告；
9. 完整安全、迁移、恢复、长数据和离线分发门。

### 9.2 建议移出 4.0

- 频道、私信、在线状态、视频会议等通用协作套件；
- 多人同时修改同一 Mission 的实时共编；
- 强制云账号和中心化事实源；
- 自动迁移 API Key、Cookie 或登录态；
- 无确认的自动换机、换模型或换执行者；
- 完整移动端工作台；
- 通用插件市场和第三方自动执行生态；
- 跨离线设备无法证明的强 exactly-once 承诺。

## 10. Traveler 解锁、但不必全部塞入 4.0 的方向

### 10.1 Mission-first 团队协作

任务分派、评论、角色、审批矩阵、团队“需要你”、依赖、SLA 和交接队列围绕 Mission 展开。它可以借鉴 Slack 的沟通效率，但不复制频道作为中心。

### 10.2 持续自动化与例外运营

定时、文件/邮件/Webhook 触发、长期 Mission、失败降级、依赖和自动归档。目标从“用户盯着任务执行”变为“系统持续运行，只把例外交给人”。

### 10.3 私有 Agent 计算网络

把多台个人或团队设备登记为能力节点，根据 OS、工具、模型、成本、性能和隐私约束选择执行环境。Task Capsule、Waypoint 和 Execution Lease 是这条路线的可信地基。

### 10.4 组织记忆与 Playbook 沉淀

把跨旅程的决定、失败方案、证据和验收结果沉淀为可审阅知识；多次相似任务后提议生成 Playbook，但必须由人确认范围、版本和失效条件。

### 10.5 Artifact-first 协作

文档、表格、代码、演示稿和数据集成为一等成果对象；审阅围绕差异、依据、责任人、接受/拒绝和逐项回退展开，而不是围绕聊天消息展开。

### 10.6 外部协作门户与垂直工作台

给客户、供应商或审核者开放最小范围的回答、上传、批准和验收入口；在通用合同稳定后，再发展法务、研究、财务、内容、研发和运维等领域 Mission schema。

## 11. 候选阶段门

沿用 Pretender“系统证据与人因证据分账”的纪律，但 Traveler 必须新增跨设备、传输和接管维度。

| 门 | 含义 | 最低证据 |
|---|---|---|
| **Concept Ready** | 北极星、三种传输模式、非目标、威胁模型和失败语义拍板 | 代表旅程走查 + 决策记录 |
| **Data & Contract Ready** | Mission 1:N、Journey Leg、Waypoint、Transfer、Lease、Capability、Evidence schema 稳定 | 迁移、崩溃、重放和兼容 e2e |
| **Capsule Ready** | 同机往返与另一台干净机器的离线导入可重复验证 | 内容保真、能力对账、凭据排除、篡改拒绝 |
| **Product Ready** | 真实发送者/接收者能理解交接、控制权和安全续办 | 外部受试者交接研究，不用内部脚本冒充 |
| **Release Ready** | 安全红队、长期数据、断网/恢复、版本迁移和分发物全绿 | Full/Slim/Release + 兼容/回滚报告 |

### 11.1 候选北极星指标

- **事实保真**：支持范围内导出—导入后的 Mission 权威事实覆盖率 100%，无静默丢失；
- **秘密隔离**：凭据测试语料泄露为 0，所有目标端凭据均重新绑定；
- **完整性**：被篡改或缺块 Capsule 的执行态导入拒绝率 100%；
- **副作用安全**：重放、重复导入、崩溃与接管场景中的重复不可逆动作数量为 0；
- **诚实降级**：能力差异、缺失文件和恢复等级 100% 显式，不静默换工具或重做高风险动作；
- **恢复可靠性**：支持旅程的重启/断网后权威状态不丢失，目标 100%；
- **人因理解**：用户在 10 秒内正确回答“任务在哪里、谁有执行权、下一步是什么、哪些不能撤销”，正确率目标 ≥90%；
- **续办成功**：正式支持的跨设备/跨接手者任务在外部测试中的成功续办率目标 ≥95%。

性能阈值需在 Concept Ready 阶段按 Capsule 体积、事件数、文件数、磁盘和硬件档位冻结；概念稿不提前写一个脱离数据集的统一秒数。

## 12. 候选实施顺序（不编号波次）

### T0 · 概念与威胁模型

- 冻结三种传输模式、核心旅程、非目标和用户词汇；
- 对路径逃逸、敏感信息、篡改、重放、撤回、过期、离线双执行和恶意附件建模；
- 决定 Mission 1:N 前置关系及跨设备身份策略；
- 用纸面 Capsule 和两台干净机器演练完整交接。

### T1 · 同机 Capsule 往返

- 完成 manifest、内容寻址、只读报告、导入隔离区和 schema 迁移框架；
- 同机导出—删除可丢副本—重新导入，验证事实、文件和恢复合同；
- 先支持 read-only / fork，不提前宣称正式移交。

### T2 · 跨设备离线续办

- 在干净设备上完成能力对账、路径映射和凭据重绑；
- 建立 Journey Leg、Waypoint 与四级恢复合同；
- 覆盖不兼容版本、缺文件、断电、包损坏和大文件场景。

### T3 · 人与人正式移交

- 上线 offer/accept/reject/revoke/expire 与 Execution Lease；
- 来源端冻结、接收端接管、归还和失败恢复语义闭环；
- 增加只读审阅、决策范围和外部受试者交接验证。

### T4 · 回程、硬化与发布

- Evidence Bundle、回程 Capsule、差异比较和显式冲突处理；
- 安全红队、长期数据、离线分发、迁移/恢复和可访问性终审；
- 达标后才执行 Traveler 版本三角、用户手册、Release Notes 与分发物正名。

## 13. 与 Pretender / 3.1 的版本关系

建议顺序：

1. **Pretender 3.0.0**：完成正式外部人因验证、P4 终审、默认切换和发布；
2. **Pretender 3.0.x**：吸收真实用户反馈，保持经典壳安全回退；
3. **Pretender 3.1 候选前置**：完成已明确延后的 Mission 1:N Session、身份与迁移语义，并执行经典壳退出评审；
4. **Traveler 4.0.0**：在稳定领域地基上交付可迁移任务旅程。

Traveler 可以现在开始概念、威胁模型和合同研究，但产品代码不应在 Pretender 的 Product Ready / Release Ready 之前抢跑。若后续决定把 1:N 合并到 Traveler 而不单发 3.1，必须正式修订 Pretender 的既有拍板记录和兼容承诺，不能静默改线。

## 14. 主要风险与反模式

1. **Slack 化**：频道、消息和在线状态吞噬 Mission 心智，重新制造“从聊天里找任务”的问题；
2. **把复制当迁移**：只打包聊天和文件，不携带状态、权限、恢复等级与副作用账；
3. **跨设备 exactly-once 幻觉**：离线双执行无法被证明时仍宣称不会重复动作；
4. **凭据漫游**：为了“无感继续”打包登录态，扩大泄露与越权面；
5. **静默降级**：目标端缺工具后自动换模型/方法，导致结果、成本和风险改变；
6. **合并幻想**：把两个 Fork 的决定、权限和外部副作用像文本一样自动合并；
7. **包体失控**：默认复制整个工作区、依赖和缓存，使 Capsule 无法审阅和传输；
8. **隐喻过度**：旅程、驻点、行李等词遮蔽“导入并检查 / 取得执行权 / 重新授权”等安全语义；
9. **生态过早**：协议尚未稳定就开放第三方 Capsule 或自动执行市场，永久固化信任缺口；
10. **抢跑 Pretender**：用未来规划掩盖当前 Product Ready / Release Ready 的未完成门。

## 15. 待拍板问题

1. Traveler 4.0 是否同时承诺“自己的跨设备续办”和“正式交给另一个人”，还是后者先以 Preview 提供；
2. Mission 1:N 是否必须作为 Pretender 3.1 独立发布，还是只作为 Traveler 的数据前置分支；
3. Transfer 模式下来源端冻结到什么粒度：整张 Mission、当前 Run，还是只有高风险执行权；
4. Capsule 的默认文件策略：全内嵌、按大小阈值、内容寻址外部包，或三者组合；
5. 第一版身份与签名采用本机密钥、组织证书还是用户导入公钥；
6. Relay 是否进入 4.0，若进入，它只搬运密文还是也承担在线租约协调；
7. 回程成果与来源端新变化如何比较，哪些冲突必须生成 Intervention；
8. 无 Traveler 接收者的只读报告允许展示哪些原文和附件；
9. Capsule schema 的向前/向后兼容窗口和只读降级期限；
10. 用户界面中“Traveler / 旅程 / 驻点”等隐喻的使用范围与安全动词白名单。

## 16. v0.1 建议结论

Traveler 最有价值、也最能复用 Pretender 投资的定位是：

> **以 Task Capsule 为传递单元，以 Waypoint 为安全续办点，以 Execution Lease 表达控制权，以 Evidence Bundle 完成交付回程，让同一张 Mission 可以在设备、环境和接手者之间可信移动。**

4.0 应优先交付 local-first、单一活跃执行权和可审阅的离线交接；实时多人共编、强制云服务和自动路由应留在合同稳定之后。Traveler 最终可以成为团队协作、持续自动化、私有计算网络和组织记忆的共同地基，但概念立项时只冻结核心原语，不把所有可能方向塞进一个版本。
