# External bot body retention

M5-B1 adds an explicit local preview and commit operation. Nothing expires automatically. The selected 7, 30 (initial selection), 90 or 365 days is a minimum age measured from acceptance, business completion and the latest sending or manual retry fact. Reading or archiving does not restart that age.

Read inbox-only messages can qualify. Control deliveries must be archived, have completed or failed execution, zero action failures/proposals and a complete action contract, and a known sent/failed/cancelled delivery. Definite failures are the explicit results produced by the current adapter or predispatch caller. A failed label with unknown provenance, any unknown result, live actor, unsettled result or live sender is excluded. This conservative release does not resolve pending actions or reconcile unknown platform sends.

The settings panel previews at most 100 bodies, displays the count and cutoff, and requires a separate confirmation. Both POST routes use the existing local token and origin gates. A ten-minute, process-bound HMAC token binds request ID, period, cutoff, selected IDs and complete current record fingerprints. Commit rechecks time, record fingerprints, terminal eligibility and all three runtime ownership maps inside the existing state chain. A single durable write removes selected body rows and adds receipts; failure does not partially change bodies or receipts. Repeated committed request IDs return their original receipt even after expiry or process restart; a different token with that ID conflicts. Uncommitted previews cannot authorize removal after expiry/restart.

Payload5 actually removes original message text, reply text and unneeded source labels/identifiers from this ledger, freeing its 1000 active body capacity. It retains up to 4096 permanent body-free receipts containing an item ID, hashed source identity, original content hash, acceptance time, terminal execution/sending facts, the current attempt and full bounded manual retry history. Up to 4096 reclamation request receipts retain request ID, token hash, count and time. Bounds refuse new reclamation instead of deleting old receipts. New accepted messages still require an active body slot and the existing 40 MiB ceiling. This is bounded capacity, not unlimited history.

Repeated authenticated callbacks with the same reclaimed message identity and content only ACK; changed content conflicts, including during later pairing. Durable retry/cancel requests retain their original receipts but cannot start a fresh reply after its source body is reclaimed. The UI never automatically repeats a reclamation POST after an unconfirmed response. The module preserves its one outstanding request through panel recreation and lets the user explicitly check that same request. A full page reload loses an unconfirmed client draft; already persisted server receipts continue to deduplicate it.

Store schema/AAD1, `external-bots/state-v1.json`, WorkDataStore encryption and the shared transaction lifecycle are unchanged. Payload1–4 remain readable until an actual successful reclamation upgrades the entire business payload to 5. Older readers refuse the whole ledger. Active payload4 retry history survives upgrade, subsequent admissions and further retry/cancel/archive operations.

Reclamation is ordinary file replacement, not secure SSD erasure. It does not delete conversations, imported drafts, platform copies, exports or historical backups. Reclaimed replies can no longer be resent from this ledger. B2/C, workflow handoff/templates, real QQ/Feishu journeys, M3/M4 and final packaging remain separate unfinished parts of 3.1.

Setup inspection's `evidence.scope` is `retained_bodies`. Its compatible `receivedMessages` and `confirmedReplies` counters describe only currently retained body records for that connection, not lifetime totals. A lower count after reclamation does not undo acceptance, execution or confirmed platform delivery. The body-free receipts retain those facts, but intentionally omit connection identity; inspection does not invent per-connection lifetime aggregates from them. The setup hint and model tool guidance state this limitation explicitly.

Author checks use only real production functions in memory/synthetic TEMP and static gates. `external-bots-retention.e2e.js` and `external-bots-retention.browser.e2e.js` are prepared for independent real HTTP/browser execution; preparation is not a passing result. Retention-specific tests include failure atomicity, live-state exclusions, full capacity release, bounded receipts, exact old-reader refusal, real adapter outcomes, callback/retry/cancel deduplication, stale cursors and late UI ownership.

Independent validation, 2026-10-30: the permanent HTTP and browser retention journeys, existing bot/control/work-data/channel regressions and final retry browser journeys were exercised on isolated synthetic data. The final terminology revision passed two retention browser runs, two retry browser runs and repository hygiene. The retained R5 full unit phase passed 4,385 tests (26 conditional skips, zero failures); after its six static failures were repaired, all 82 original static scripts passed separately. These are separate runs, not a relabeled green fast process. Evidence and original failures: [retention batch](../optimization-plan/evidence/m5-retention-20261030.json). The broader encrypted crash/bad-cipher/active-eligibility matrix and remaining M5/3.1 delivery are still pending.
